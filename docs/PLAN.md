# PLAN.md — 작업 계획 (누가 무엇을 어떤 순서로, 어디까지 됐나)

> 오케가 쓴다. 예외 하나: **5절 품질 비교표**는 시험 적용 서브에이전트(「표본」 행 — 데이터 일부에 해법을 돌린 결과, M2)·코어 워커(「전체 기간」·「민감도」 행, M3)가 자기 행만 쓴다. 쓰는 순서: M1 에 2절 R 행 → 조사 도는 동안 2절 C·G·S → M2 설계 논의에서 항목이 닫힐 때마다 2~5절. 무엇을 왜 만드나는 SOLUTION, 서비스 구조는 ARCHITECTURE. 바뀐 줄은 지우지 않고 `~~옛~~ → 새 (D번호)`.
> 갱신 이력: (HH:MM 무엇이 왜 — decision ID)

## 1. 시간 기준선
setup.sh 가 채운다

| 기준선 | 안내(종료 N분 전 — 종료 시각은 과제설정 4절) | 실제 시각 | 태그 |
|---|---|---|---|
| 문제 확정 | 140 | | `define` |
| 솔루션 확정·구현 시작 | 110 | | `solution` |
| 얇은 결과 시연(피드백 DM 1차) | 80 | | FEEDBACK 첫판 |
| 피드백 끝·동결 | 40 | | `feedback` |
| `final` 커밋 | 20 | | `final` |
| 제출 버튼 | 0 | | |

실제 시각은 그 신호를 처리하는 턴에 `TZ=KST-9 date +%H:%M` 으로 적는다. 기준선은 참고다 — 늦어도 절차가 달라지지 않고, 사용자가 줄이기로 정한 것만 `$decision`. **연장·중단 통제 메시지가 오면 과제설정 4절을 먼저 고치고 위 줄의 안내 시각을 다시 계산한다.**

## 2. 요구·제약 추적 표 (목표와 제약식을 한 표에 — 여기 없는 제약은 아무도 검사하지 않는다)
행의 출처: PROBLEM 3절 요구 ID 전부(R) · PROBLEM 4·6절 규칙의 **모든 수치·한도·불가 조건**(C — 자원 상한·정원·시간 한도·금지 조건처럼 원문에 숫자나 「~해야 한다/~하지 않는다」로 있는 것 전부) · PROBLEM 5절 성공 기준(G) · 과제설정 2·3·5절 제출·인프라·금지(S). 종류: 목표 / 하드 제약(어기면 결과 무효) / 소프트 제약(어기면 품질 저하) / 가정(실무자가 주지 않은 숫자). **하드 제약 행에 테스트 이름이 비면 솔루션 확정 못 한다.** 코어·통합 보고는 하드 행마다 지켰다 / 깨졌다 / 측정 안 함.
