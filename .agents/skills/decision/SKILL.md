# decision — 결정 기록

`docs/DECISIONS.md`(없으면 `# DECISIONS` 로 생성)에 한 결정 = 한 블록을 추가한다. 기록 대상: 방향을 바꾸는 결정 · 범위를 자르는 결정 · 대안이 있었던 선택 · AI 제안을 사용자가 바꾸거나 거절한 순간.

```
## D<다음 번호> — <결정 한 줄> (<시각 KST>)
- 이유: <이 제약에서 왜 이것이 최선인가>
- 기각한 대안: <대안> — <기각 이유>
- 제안: <AI(어느 탭)·사용자·실무자> → <채택·수정·거절>
- 확인: <테스트 이름·통과 수 | 실무자 확인 DM 답변 N | 화면에서 직접 봄 무엇> (선택 — 아래 세 종류 중 하나)
- 보장 범위: <이 결정이 맞다고 보장하는 조건·데이터 범위 — 그 밖은 미확인>
- 영향: <바뀌는 파일·범위> (선택)
```

**확인 세 종류**(외우기 쉽게 고정 — 설명 탭이 서술형 연습 때 꺼내 준다): ① **테스트**(이름과 통과 수) ② **실무자 확인**(DM 몇 번째 답) ③ **화면에서 직접 봄**(무엇을). 확인한 게 없으면 「확인: 없음」이라고 쓴다.

- 결정자·근거·대안을 지어내지 않는다. AI가 맡은 기술 선택은 조사한 근거와 대안을 스스로 기록한다. 사용자 판단이 필요한 업무 방향·범위 변경만 묻고, 아직 결정되지 않았으면 「제안/미결」로 남긴다.
- 사실·가정·판단을 구분한다. 미검증 선택은 확인: 없음 + 다음 검증을 쓰고, 나중에 결과가 달라지면 원 결정을 지우지 말고 D번호를 연결해 정정한다.
- 범위를 자른 것도 결정이다 — 무엇을 왜 잘랐는지가 자원 운용의 증거다.
- 사용자가 AI 제안을 바꾸거나 거절한 개입도 기록한다(사람의 판단이 들어간 자리가 채점 표면이다). 「제안」 줄은 2차 공식 평가 문구 「AI 제안의 채택·수정·거절 이유」를 받는 자리 — 채택이어도 누구의 제안인지 적고, 수정·거절이면 이유 줄에 왜를 쓴다.
- 추가한 블록만 출력해 보여 준다.
- DECISIONS 쓰기 소유자는 오케다. 워커·검토자는 결정 제안과 근거를 오케에게 전달하며 공유 파일을 직접 고치지 않는다.
- 커밋: 중요한 결정(방향 변경 · 범위 자르기 · 사용자가 AI 제안을 바꾼 순간)만 바로 `git commit -m "decision: <무엇>" -m "<왜·기각 대안>"`. 점검표 논의 중의 작은 결정은 다음 커밋에 함께 넣는다.
