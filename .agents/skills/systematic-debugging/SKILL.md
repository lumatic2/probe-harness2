# systematic-debugging — 원인을 확인한 뒤 수정

출처: [Superpowers systematic-debugging](https://github.com/obra/superpowers/tree/2ce8aa1/skills/systematic-debugging), MIT(`LICENSE-superpowers`), 원본 반입 2026-10-27. 대회판 수정 2026-10-30: 핵심 조사 흐름을 유지하고 미반입 스킬 의존·개인 환경 예제·반복 문구를 제거했다. 부속 기법 문서는 반입하지 않았다(원본 저장소 참고).

## 1. 실패를 고정한다

- 실패 명령·기대/실제·종료코드·입력·관련 버전/경로를 기록한다. 스택 추적과 바로 전 변경을 읽는다. 비밀값·원본 개인정보는 로그에 넣지 않는다.
- 같은 입력으로 재현한다. 비결정적이면 빈도·조건부터 좁히며 재현되지 않은 원인을 확정하지 않는다.
- 환경 실패(권한·설치·네트워크)와 제품 결함을 구분한다. 작업이 시작도 안 됐는데 제품이 틀렸다고 고치지 않는다.

## 2. 끊어진 경계를 찾는다

입력 → 파싱 → 규칙/집계 → 저장/API → 화면 중 실패 지점을 확인한다. 각 경계의 입력·출력을 필요한 만큼 관측하고 정상 사례와 차이를 비교한다. 로그에는 키 유무·형식·행 수를 쓰며 키 값이나 전체 데이터를 출력하지 않는다.

호출이 깊으면 실패 지점에서 호출자 쪽으로 한 층씩 거슬러 입력을 확인한다. 타이밍 문제면 조건이 참이 될 때까지 기다리는 코드로 고치고, 임의 sleep을 늘려 덮지 않는다.

## 3. 가설 하나를 반증한다

`가설: X 때문에 Y가 발생한다. 근거: Z. 확인: <가장 작은 실행>`을 적고 변수 하나만 바꿔 확인한다. 실패하면 새 증거로 가설을 바꾸며 여러 수정안을 한꺼번에 쌓지 않는다. 원인이 불명확하면 조사한 범위와 미확인 지점을 보고한다.

## 4. 최소 수정과 재검증

- 수정 전에 가장 작은 재현을 확보한다. 지속될 제품 버그는 회귀 테스트를 작성해 FAIL을 확인한다. 도구/환경 문제는 실제 실패 명령·관측으로 재현하고 의미 없는 테스트를 만들지 않는다.
- 자기 소유 파일에서 확인한 원인만 고친다. 관련 없는 리팩터링·의존성 추가를 묶지 않는다.
- `.agents/skills/verify/SKILL.md`로 **같은 실패 명령**을 재실행하고 영향받는 검사를 돌린다. 실행/표시/저장 중 문제였던 경로도 다시 확인한다.
- 같은 원인으로 2번 실패하면 멈추고 위로(워커 → 오케, 오케 → 사용자) 재현·시도·남은 가설·필요한 결정/정보를 돌려준다. 구조 문제는 근거로 제안하며 임의로 전면 재작성하지 않는다.
- 검증 실패를 만들기 위해 정상 코드를 일부러 망가뜨리지 않는다. 새 테스트의 실패가 바로 그 버그를 잡는지 확인한다.

## 결과

`증상 → 확인된 원인(미확인이면 그렇게) → 최소 수정 → 같은 명령의 전/후 결과 → 남은 한계`를 반환한다. 검증은 verify가 기록하고, 구조/범위 결정은 오케가 decision으로 남긴다. 조사 기록을 별도 문서로 매번 늘리지 않는다.
