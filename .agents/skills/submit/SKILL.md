# submit — 제출 점검 (M5)

> **M5 서브에이전트로 띄워졌거나 독립 탭으로 열렸다면**: 이 파일 + `docs/과제설정.md`(제출물 배치·필수 파일·금지) + 아래 항목이 가리키는 작업 폴더 안 파일을 읽는다. 작업 폴더 밖(`~/.codex/skills/`)은 찾지 않고 제작 의도는 묻지 않는다. 지적 목록(심각한 순)을 `docs/judge/점검-<HHMM>.md`(시각은 `TZ=KST-9 date +%H%M`)에 쓴다. 검증 기록은 `docs/VERIFICATION.md`·`docs/verify-logs/` 에 남는다(5번 클린 재현 · 6번 `verify.sh` 자동 기록). 그 밖의 파일은 고치지 않고 커밋하지 않는다. 마지막 메시지는 결과 문서 경로 + 결론 3줄. 처분은 오케, 수정은 소유 워커, 청소 목록 삭제만 오케.
> **독립 탭이면**: 첫 행동으로 `echo "제출점검 $CODEX_THREAD_ID 탭 보고→오케" >> docs/세션.txt`. 끝나면 오케 UUID 로 `codex queue --thread <오케 UUID> --message "[제출점검→오케] 끝 — <결과 문서 경로> · 결론 3줄"`. 수정 뒤 재점검 요청이 오면 같은 탭에서 영향받은 검사만 다시 한다.

제출 미리보기에는 일부 파일만 보이고 확정 뒤엔 고칠 수 없다. 아래를 순서대로, 각 항목에 통과/지적/미확인/해당 없음(이유). 시작 시 `git rev-parse HEAD`와 `git status --short`를 기록한다. 점검 대상은 그 커밋이며 검사 중 제품 파일이 바뀌면 영향받는 검사를 다시 한다.

1. **필수 파일명·원문 보존**: `docs/과제설정.md` 2절의 산출물 표대로 파일명·경로가 정확히 있나(`ls`). **루트 README 취급이 「보존」이면 `git diff <scaffold 커밋> -- README.md` 가 비어 있어야 한다**(원문 훼손은 제출 실패급). **과제 원본 보존**: `git diff --name-status --diff-filter=DRM <scaffold 커밋> HEAD` 에 과제설정 1절의 파일이 나오면 지적한다(「채움」 양식은 제외). git 이 추적하지 않는 원본은 `ls` 로 있는지 본다. 공식 답변 파일(Q1~Q3 류)에 「(답변)」 빈칸이 남았나, 사용자 사실 확인 표시가 있나. 실행 안내 「합의와 담당자 재량」 표의 각 줄에 `[답변N]` 이 있고 `docs/interview/` 원문에 그 답이 실제로 있나 — 없는 합의를 적지 않았나.
2. **실행 안내 증거**: `python3 harness/tools/evidence_check.py <실행 안내 파일>` → 0(과제 양식이면 「된다」 표가 없는 절은 exit 2 가 정상 — 그때는 절마다 명령·결과가 실제 커밋과 맞는지 눈으로 대조). 안내의 대표 수치·명령·포트가 **점검 기준 커밋**의 실물과 같은가. 모듈 README 도: `ls src/*/README.md` 가 실행 안내 파일 「구조와 설계 근거」 표의 모듈과 1:1 이고, 각 파일의 검증 명령을 실제로 한 번 돌려 통과하며, 언급한 파일·함수가 실제로 있다(`evidence_check` 는 「된다」 표가 없는 모듈 README 에 exit 2 — 그건 정상). 「된다」 표의 칸마다 테스트 이름·`파일:줄`·명령이 있고 언급한 파일이 전부 존재. 「안 된다 / 안 했다」 절이 있나(선택한 판단과 근거·검증 결과·남은 한계 — 공식이 요구한 4요소). 채점용 문서(`ARCHITECTURE` · `SOLUTION` · `PROBLEM` · `DECISIONS`)의 모듈·기법·수치·언급한 파일이 점검 기준 커밋의 실물과 같은가. 어긋나면 지적한다.
2-1. **「AI 활용 기록」 대조**: 실행 안내 파일(과제설정 2절)에 이 절이 있고, 역할 수 · 위임 수 · 재작업 수 · 기준선 대비 실제 시각이 `docs/세션.txt` · `docs/DECISIONS.md` · `git log` · `docs/PLAN.md` 「시간 기준선」 를 직접 센 값과 같다(`git log` 시각이 UTC 면 KST 로 바꿔 대조). 다르면 지적.
3. **교체 지점 표**: 환경변수·외부 서비스·AI 모델 교체 지점이 실행 안내 파일 표에 빠짐없이(변수 하나 누락도 부분 충족이 된다). 환경 변수는 코드가 읽는 변수(`grep -rhoE "process\.env\.[A-Z_]+|os\.environ\['[A-Z_]+|getenv\('[A-Z_]+" src/`)가 실행 안내 파일 「환경 변수」 표에 전부 있나.
4. **낡은 문서 청소**: 빈 틀(`docs/mail/` 미사용 · `harness/starter/` 안 쓴 갈래 · 빈 절이 남은 docs)·스캐폴드 잔재·중복 문서 삭제 목록을 만든다(삭제는 오케스트레이터). 과제설정 1절의 과제 원본은 목록에 넣지 않는다.
4-1. **제품 미사용 부품·비용**: `harness/starter/shadcn/INTEGRATION.md`의 정리 절차를 대조한다. 개발 카탈로그·다른 도메인 견본·미사용 라우트/API·가상 문구가 제품에 남았는지, 메뉴만 숨겨 번들/직접 URL에는 남았는지 확인한다. AI 기능이 있으면 입력·출력/시간 제한·중복 전송·재시도·관측 가능한 사용량과 예산 요구 충족을 확인한다. 없는 상한을 있다고 주장하지 않는다. 수정은 소유 워커, 삭제는 오케가 하며 정리 뒤 검증된 커밋을 다시 받는다.
5. **클린 재현**: 검사 대상 제품 변경을 오케가 먼저 커밋했는지 확인한다. 미커밋 제품 변경이 있으면 현재 상태를 클린 재현했다고 하지 않는다. `mktemp -d`로 만든 **레포 밖** 임시 폴더에(레포 안에 `clean-room` 류 폴더를 만들지 않는다 — 제출물에 섞인다. 끝나면 지우고, 삭제가 막히면 경로만 보고한다. 이 폴더는 `AGENTS.md` 「폴더」의 허용 예외다 — 「파일은 이 안에서만」을 이유로 건너뛰지 않는다) `set -o pipefail; git archive HEAD | tar -x -C <임시>` 후 실행 안내 파일 절차 그대로 설치·검증·실행(서버는 `PORT=<빈 포트>` 로 — 3000 은 통합 서버 탭이 쓰고, 끝나면 자기가 띄운 것만 끈다. 포트 지정을 안내대로 할 수 없으면 그 자체가 지적이다). 새 폴더 안의 로컬 합성/허용 데이터로 실행하고 실제 외부 전송·쓰기 부작용이 있는 명령은 격리하거나 미확인으로 보고한다. 결과를 `docs/VERIFICATION.md` 에 기준 커밋·시각과 함께.
6. **전체 테스트**: `harness/verify.sh "<전체 테스트 명령>"` PASS.
7. **용량·저장 상태·커밋**: `du -sh .` 가 10GB 이하(제출은 폴더 전체 기준 — `node_modules`·데이터 복사본 포함). `git status --porcelain`에서 제품 변경과 검사 보고서 변경을 구분한다. 검사 보고서는 오케가 취합해 커밋하고, 제품 변경은 재검증한다. 최종 빈 상태 확인은 보고서 커밋 뒤 오케가 한다. 사용자는 루트 `메모.md` 말고는 에디터로 고치지 않으므로 디스크 = 제출물이다 — 사용자에게 확인을 요청하지 않는다.
8. **금지 패턴**: `python3 harness/tools/security_check.py` 막는 것 0(`.env` 추적 · 키 문자열) + 개인정보.

점검은 제출 동작이 아니다. 제출 버튼·확정·공개 전환을 대신 실행하지 않는다. 사용자에게 확인된 제출 준비 상태와 실제 누를 단계만 전달한다. 제출 경로가 전체 디스크라면 git archive 재현만으로 충분하지 않으므로 ignored·미추적 파일도 필수 파일·비밀·캐시 범위에서 따로 대조한다.

출력: 기준 커밋·명령·종료코드·통과/지적/미확인 목록 → 오케스트레이터가 지적을 처리하고 `final` 커밋. 공식 답변 파일은 동결 때 사실 확인 중인 초안이다 — 형식·존재만 본다.
