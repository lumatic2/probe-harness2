# M4 — 구현 · QA · 수정 (오케 + 워커)

## 핵심 4줄
- 목표: 솔루션 확정 때 정한 모듈·계약·엣지 대처가 그대로 코드가 되고, 사용자 흐름이 실제 데이터로 한 번 관통해 돌아간다
- 종료 조건: 「QA 끝」 — 사용자가 플랫폼 Browser 로 기능·화면을 보고 지적을 끝냈고, 오케와 끝난 것·안 된 것을 합의했다
- 담당: 코어 워커는 계산, 통합 워커는 서버, 검증 워커는 E2E·Docker·실행 재현, 화면 워커는 화면과 **사용자 QA 대화**, 오케는 판단·재지시·브리핑
- 증거: 계약 테스트 초록 · E2E · PLAN 5절 「전체 기간」 행 · 사용자 첫 화면 확인 · `build` 커밋

사용자가 치는 것은 QA 지적 · 「구현 끝」(오케 탭) · 「QA 끝」(화면 탭) · 끝 되읽기에 「맞다」 — 그 밖의 결정은 솔루션 확정·설계 OK 때 끝났고, 새로 필요하면 오케가 묻는다.

## 역할 — 몇 개 · 무엇은 M3 에서 정했다
워커 수 · 이름 · 맡는 모듈은 M3 점검표 ⑫ 에서 사용자와 정했고 `docs/brief/<역할>.md` 에 있다. 역할별 할 일은 **`harness/roles/워커/`** 에 역할마다 한 파일이다 — 워커는 `공통.md` 와 자기 역할 파일만 읽고, 오케는 재지시할 때 그 역할 파일만 연다(이 문서에 옮겨 적지 않는다). 탭 이름은 역할 이름(코어 · 통합 · 검증 · 화면 · 서비스), 구현 워커가 모듈을 하나씩 맡으면 모듈 이름.

| 역할 | 한 줄 | 파일 |
|---|---|---|
| 공통 | 시작 · 소유 경로 · 커밋 본문 「설명:」 줄 · 보고는 셋뿐 | `harness/roles/워커/공통.md` |
| 코어 | 순수 계산 · 전량 1회 · 품질 비교표 · 민감도 | `harness/roles/워커/코어.md` |
| 화면 | 화면 설계대로 등록·부품·안내 · 사용자 QA 상대 · 제출 정리 | `harness/roles/워커/화면.md` |
| 통합 | 서버를 살려 둔다 · 재빌드 · 첫 화면 보고 | `harness/roles/워커/통합.md` |
| 검증 | E2E · 서버 전량 · Docker·재현 · 「만약」 세 가지 | `harness/roles/워커/검증.md` |
| 서비스 | (켰을 때만) API·DB 층 | `harness/roles/워커/서비스.md` |

과제가 작아 한 탭으로 충분하면 통합이 검증까지 맡는다 — M3 점검표 ⑫ 에서 정한다.

## 오케 — M4 시작 턴
모든 「준비됨」이 오면(`M3.md` 「설계 OK」 6) 사용자에게 한 줄: `지금 칠 것 없음 — 설명 탭에서 서술형 연습을 해도 됩니다. 첫 화면이 오면 화면 탭에서 QA 합니다(예상 HH:MM).`

## 오케 — 완료 queue 가 올 때마다 (읽고 판단만, 다시 돌리지 않는다)
- 답은 **지시나 결정이 있을 때만**. 워커가 상태 보고를 반복하면 「완료·질문·새 오류 때만 보고」 한 줄로 한 번 바로잡고 그 뒤는 무시한다.
- 본다: 검증 출력이 초록인가 · security_check 0 인가 · 데이터 과제면 `schema.json` 규칙이 assert 목록과 같은 점검인가(두 벌이면 재지시) · **경계** — 코어 모듈이 HTTP·DB 를 import 하지 않는다(`grep -rlE "fastapi|flask|django|starlette|express|node:http|http\.server|sqlite|psycopg|pymysql|mongo" src/<코어>/` 가 비어야 한다) · 「된다」 표 줄이 PLAN 2절 ID 와 맞는가.
- 빠진 것은 같은 UUID 로 **변경점만** 재지시. 통과는 PLAN 3절 상태에 한 줄. 오케가 직접 `harness/verify.sh` 로 재실행하는 것은 **같은 원인 2번 실패 뒤 1회**(`docs/DECISIONS.md` D0) — 같은 원인 2번 실패면 브리프를 고쳐 다시 보낸다.
- **코어 완료를 받은 턴에 독립 재계산 서브에이전트 하나**를 띄운다(`wait_agent` 없이 — 구현·QA 가 도는 동안 돈다. 이것 하나가 계약 대조와 숫자 재계산을 같이 한다 — 따로 두 번 띄우지 않는다). 구현과 **별개로** 원본에서 다시 센다. 프롬프트 = 원본 경로 + 규칙 + 셀 대상(PLAN 5절 「독립 재계산 대상 숫자 3~5개」) + 출력 계약 파일이 있으면 「원본에서 기대 집합을 만들어 대조」. **`src/`·`tests/`·`docs/experiments/` 는 읽지 말 것**을 박는다. 결과는 `docs/VERIFICATION.md` 「기대값」 절에 숫자·명령, 어긋나면 코어에 재지시. **최적화 과제면 두 가지를 더 시킨다**: ① 풀이와 별개 코드로 **하한**을 센다(정원 하한 `ceil(인원/정원)` · 제약을 하나 풀었을 때의 최솟값 등 쉬운 것 1~2개) → 제품 달성값 옆에 「하한 N · 달성 M · 차이 %」 — 하한과 같으면 최적, 아니면 그 차이가 남은 한계다. ② 검사기(제약 위반 판정)가 있으면 **정상 해 1건을 일부러 망가뜨려**(시간 1초·인원 1명) 검사기가 거부하는지 테스트 1개.
- 코어 보고에 「표본과 크게 다름」·「기본값에 민감」이 있으면 받아들일 한계가 바뀐 것이라 사용자 몫이다 — 사용자에게 3줄(가장 나쁜 사람 · 악화 규모 · 자원)과 추천(이대로 / 대처 바꾸기) → 사용자가 정하고 `$decision`. 보고의 「결정 필요」가 기술 판단이면 오케가 정한다. **실무자만 답할 수 있는 업무 가정**(예외·상한·제외 대상)이면 `[오케→DM] M4 확인 질문: <한 토막>` — DM 이 한 질문만 짧게 보내고, 답이 오면 `$decision` 뒤 소유 워커에 재지시. 기다리는 동안 워커는 PLAN 2절 「가정」 행의 기본값으로 계속 가고 그 사실을 보고에 적는다.
- 기다리는 동안: 「된다」 표 줄을 실행 안내 파일에 모은다 · FEEDBACK 첫판 재료 · 공식 답변 파일(과제설정 2절) 초안에 **지금까지 사용자가 실제로 한 판단**을 적어 둔다(막판에 몰면 사실 확인을 못 한다).

## 첫 화면 → 사용자 QA · 얇은 결과 시연
화면이 없으면(과제가 파일 출력이거나 npm 이 막혀 안 세웠을 때) 통합이 「첫 화면」 자리에 결과 파일 경로·실행 명령을 보고하고, 아래 화면 워커 몫(시연 안내 · 지적 받기)은 오케가 한다. 「QA 끝」도 오케 탭에 친다.

1. 통합의 「첫 화면」을 받은 턴에 셋: 사용자에게 「화면 탭에서 봅니다 — Browser 포트 칸 `3000` · 경로 칸 `/`」 한 줄 · 화면 워커에 `[오케→화면] 시연 안내 시작 — SOLUTION 3절·「된다」 표·BROWSER.md 로` queue · **얇은 결과 시연** — 핵심 흐름이 실제 데이터로 관통했으니 다른 모듈을 기다리지 않고 `다음 입력(오케): 「피드백 DM 시작하자」 — QA 와 겹쳐 돌아도 됩니다`(`M5.md`). 단 전체 기간 행이 진행 중이면 이 안내는 행이 들어온 뒤에 낸다(실무자에게 보일 숫자가 그 행이다). 부분 시연은 미구현 범위를 밝힌다.
   - 같은 턴에 **화면 점검 서브에이전트**를 띄운다(`.agents/skills/design-review/SKILL.md` → `docs/judge/화면-<HHMM>.md`) — 예쁜지가 아니라 ARCHITECTURE 1절 화면 설계대로 화면이 이어지는지(끊긴 흐름 · 설계와 실물의 차이 · 어긋나는 말과 숫자 · 빈 자리). 사용자 QA 와 겹쳐 돈다. 결과가 오면 지적마다 검산해 `$decision`, 화면 지적은 화면 워커에 queue, 「사용자가 직접 볼 것」은 시연 안내에 합친다. 피드백으로 화면이 크게 바뀌면 「피드백 끝」 전에 한 번 더 띄운다(동결 뒤에는 띄우지 않는다).
2. **화면 워커가 사용자의 QA 상대다** — 시연 안내 한 덩어리와 지적 처리(화면 지적은 그 자리에서 고쳐 재빌드 · 계산·데이터·범위 지적은 묶어 `[화면→오케] 지적: …` 한 번)는 `harness/roles/워커/화면.md` 「사용자 QA」. 오케는 넘어온 지적만 본다: 받을지 판단(새 요구면 「요구에 없다」 — 받을지는 사용자에게 묻고 `$decision`) → 소유 워커에 재지시하며 「고치면 화면에 직접 `[<역할>→화면] 반영 <커밋>`」을 붙인다.

## 「구현 끝」 — 사용자가 친다 (시각으로 스스로 시작하지 않는다)
모든 워커의 첫 완료를 받으면 오케가 한 번 `다음 입력(오케): 「구현 끝」 — 치면 새 기능을 막습니다` 로 알린다.
살아 있는 워커 전부에 `[오케→전체] 계획한 구현 끝 — 새 기능은 시작하지 말고 지금 것 마무리와 피드백 처분 수정만, 못 한 것은 「안 된다」로 · 모듈 README(`src/<모듈>/README.md`)를 `harness/starter/README-TEMPLATE.md` 「모듈 README 틀」대로 지금 써서 커밋` queue(모듈 README 를 여기서 받아 두면 M6 동결이 기다리지 않는다). 남은 것을 줄일지는 사용자가 묻거나 정할 때 얇게 / 안 할 것을 함께 고른다(`$decision`).

## 「QA 끝」
사용자가 화면 탭에 「QA 끝」을 치면(오케 탭에 직접 쳐도 같다) 화면 워커가 `[화면→오케] QA 종료 — 지적 N건: 자리에서 처리 n · 오케 이관 m(처리 상태) · 받지 않은 새 요구 k` 를 queue 한다. 오케가 끝난 것 · 안 된 것(실행 안내 「안 된다」에 갈 것) · 남은 지적 처리 상태를 3줄로 되읽고 사용자가 「맞다」 하면 `build` 태그 커밋 → PLAN 1절 실제 시각 → 다음 할 일 한 줄. 중요한 실패가 남아 있으면 완료로 표시하지 않는다.
