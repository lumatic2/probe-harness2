# M4~5 — 피드백 · 동결 · 점검 · 제출 (오케)

## 핵심 4줄
- 목표: 완성된 결과를 실무자에게 알리고 짚은 것을 처분해 **수용 여부를 한 번 확인**하고, 재현 가능한 제출물을 확정한다
- 종료 조건: `final` 커밋 뒤 제출 대상 경로에 미커밋이 없고, 사용자가 「검증된 것 / 안 되는 것 / 알고 제출하는 한계」를 이해했고, 공식 답변 파일이 있으면 사용자 사실 확인이 끝났다
- 담당: DM 탭이 대화, 오케가 처분·수정 지시·최종 판정, 서브에이전트가 독립 재계산과 점검 3종(제출 점검은 독립 탭도 된다)
- 증거: `docs/FEEDBACK.md` · `docs/VERIFICATION.md` 독립 재계산 · `docs/security/M5.md` · `docs/judge/` · `feedback`·`final` 커밋

경계의 뜻: 「구현 끝」 뒤 새 기능은 시작하지 않고 피드백 처분 수정은 계속 · 「피드백 끝」 뒤 제품 변경은 M5 점검 지적뿐 · `final` 뒤 서술형 연습 1~2문항 → 제출 버튼. 시각은 `harness/guides/지도.md` 「시간 기준선」(참고).

## 「피드백 DM 시작하자」
1. `docs/FEEDBACK.md` 첫판. 1절은 실제 데이터로 **먼저 돌린** 숫자와 **품질 비교표 포인터**(PLAN 5절 「전체 기간」 행 — 복사하지 않는다)만. 예정·샘플을 실제로 적지 않는다.

```
# FEEDBACK — 실무자 피드백 (M4, 살아 있는 문서)
> 모든 줄에 출처: [답변N] · [테스트:이름] · [명령:…]. 바뀐 줄은 ~~옛~~ → 새 [답변N].

## 1. 보여 줄 결과
| 성공 기준(PROBLEM 5절) | 기준선 | 지금 숫자 | 측정 명령 | 실무자 반응 |
|---|---|---|---|---|
| 품질 비교표 → `docs/PLAN.md` 5절 「전체 기간」 행(복사하지 않는다) | | | | 실무자 반응은 PLAN 표의 마지막 열에 |

## 2. 피드백 표
| F-ID | 실무자 말(원문 요약) | 분류(아래 처분 표) | 처분과 이유 | 검증(실패 출력 → 같은 명령 재통과) | 다시 알렸나 |
|---|---|---|---|---|---|

## 3. 받지 않은 것과 남은 한계 · 마지막 수용
- (새 요구 — 받지 않은 이유 · 실무자에게 말했나 · 실행 안내 「안 된다」로)
- (결과 불수용이 남은 것 — 사용자 결정 · 원인 · 공급/기준 미확인은 「미확인」으로)
- 마지막 수용: (수용 / 이의 처분 / 검토용으로 쓸 수 있음 — [답변N])
```

2. DM 탭 안내 한 줄(중간 응답으로 먼저): `DM 탭에 「harness/roles/DM.md 읽고 피드백 DM 시작해」`. 마지막 줄 `다음 입력(DM): harness/roles/DM.md 읽고 피드백 DM 시작해`. DM 이 도는 동안 오케는 DM 에 상태·독촉 queue 를 보내지 않는다 — DM 은 실무자 답이 와야 움직이고, 답은 사용자가 붙인다.
3. **같은 턴에 독립 재계산 서브에이전트**를 띄운다(`wait_agent` 없이 — 피드백이 도는 동안 돈다). 구현과 **별개로** 원본에서 핵심 숫자 3~5개를 새로 센다. 프롬프트 = 원본 경로 + 규칙 + 셀 대상만. **`src/`·`tests/`·`docs/experiments/` 는 읽지 말 것**을 박는다. 결과는 `docs/VERIFICATION.md` 「기대값」 절에 숫자·명령. **최적화 과제면 두 가지를 더 시킨다**: ① 풀이와 별개 코드로 **하한**을 센다(정원 하한 `ceil(인원/정원)` · 제약을 하나 풀었을 때의 최솟값 등 쉬운 것 1~2개) → 제품 달성값 옆에 「하한 N · 달성 M · 차이 %」 로 적는다 — 하한과 같으면 최적, 아니면 그 차이가 남은 한계다. ② 검사기(제약 위반 판정)가 있으면 **정상 해 1건을 일부러 망가뜨려**(시간 1초·인원 1명) 검사기가 거부하는지 테스트 1개 — 검사기가 통과만 내는 검사기가 아님을 보인다.

## 처분 — `[DM→오케] M4 답 N` 이 오면 (정본 — DM 파일은 이 표의 「DM 이 전하는 말」만 쓴다)
DM 이 원문을 `docs/interview/M4.md` 에 남기고 문장마다 분류 후보를 붙여 보낸다. **F-ID 와 처분은 오케만** FEEDBACK 2절에 쓴다. 기본은 **설득하고 밀고 간다** — MUST 는 채웠고 가정은 M2 에서 기본값으로 알렸고 이의가 없었다.

| 분류 | 처분 | 누가 정하나 | DM 이 전하는 말 |
|---|---|---|---|
| 버그 · 틀린 숫자 | 고친다 | 오케 | 「반영하겠습니다」 → 고친 뒤 ④ 통에 「지금은 이렇습니다」 |
| 작은 보정(표시·문구·단위 — 결과가 안 바뀜, MUST 안) | 고친다 | 오케 | 위와 같다 |
| 받지 않을 것(새 요구 · 합의와 다른 방향) | 안 고친다 | 오케 · 같은 요청이 두 번이면 사용자(`$decision`) | 세 줄 설득: 「앞서 ○○로 합의했고 → 그 기준에서 이렇게 처리했으며 → 요청대로 바꾸면 ○○(숫자)이 생깁니다. 이번에는 기존 방식으로 가고 ○○는 다음 단계 과제로 적어 두겠습니다.」 근거는 M1·M2 합의 · 데이터 · 시간 안에 되는 것만. 「기술적으로 어렵다」는 쓰지 않는다 |
| 막판 뒤집기(합의와 다른 소리) | 안 고친다 | 오케 · 사용자가 뒤집고 싶을 때만 `$decision` | 「그 부분은 앞서 ○○로 합의한 내용이어서 시간 관계상 기존 방식으로 진행하겠습니다. 의견은 기록해 두겠습니다.」 사용자에게 「뒤집기 왔음 · 기존 방식 유지」 한 줄 |
| 의미를 바꾸는 보정(결측 채우기 · 방향 대칭화 · 평균 대체 · 실적으로 수요 깎기) | 사용자가 정할 때만 정리 뷰 한 곳에서 | 사용자(`$decision`) | 결정대로 |
| 절대 안 된다(출력을 못 쓴다 · 규정 위반 · 필수 누락이 명시적) | 고친다 | 오케 `$decision` | 「반영하겠습니다」 |
| **결과 불수용**(「이 결과는 윗선에 못 올린다」류) | 사용자에게 올린다: 「대안 분석 1회(코어, N분) / 한계로 적고 검토용으로 닫기」 — 재분석을 자동으로 시작하지 않는다 | 사용자(`$decision`) | 결정대로. 「접수」(확인되면 알려 달라)는 수용이 아니다 |

- 고칠 것은 소유 워커에게 같은 UUID 로 **변경점만** 재지시하고, 완료 보고의 검증 출력을 읽어 검수한다(재실행은 `docs/DECISIONS.md` D0). 고쳐지면 `[오케→DM] 반영됨: F<n> <한 줄>` — DM 은 ④ 통에 몰아 전한다.
- 「피드백 끝」 때 남은 수정은 영향과 처리안(얇게 / 「안 된다」로)을 보이고 사용자가 정한다.

## 「피드백 끝」(DM queue) — 이 턴이 M4→M5 경계 턴이다
이 턴 첫 줄 `M4 종료 → M5 시작 (HH:MM)`. 본문에서 1~3 을 하고 바로 M5 동결로 간다. 「구현 끝」을 아직 안 쳤으면 그 queue(`M3.md`)를 이 턴에 보내고, 「QA 끝」이 아직이면 사용자에게 「QA 를 여기서 마칠까요」 한 줄을 묻는다 — 마치면 `M3.md` 「QA 끝」 되읽기와 `build` 커밋을 먼저 한다.
1. **독립 재계산 대조**: 기대값과 지금 커밋의 제품 숫자를 맞춘다(아직 안 왔으면 `wait_agent` 긴 timeout). `docs/VERIFICATION.md` 에 일치/불일치 · 기준 커밋. 불일치는 틀린 숫자로 처분한다.
2. `feedback` 태그 커밋 · PLAN 「시간 기준선」 실제 시각. 이 뒤로 제품 변경은 M5 점검 지적뿐이다.
3. 끝난 것 한 줄 · 다음 할 일 한 줄. 구현 탭은 모듈 README·점검 지적 수정이 오므로 `final` 까지 둔다.

## M5 동결 — 제출 문서를 최신 실물에 맞춘다 (배치는 `docs/과제설정.md` 2절이 정한다)
4. 제출 문서:
   - 실행 안내 파일(과제가 지정한 `HOW_TO_RUN.md` 류가 있으면 그 양식 그대로 — 절마다 무엇을 넣는지는 `harness/starter/HOW_TO_RUN-TEMPLATE.md`, 지정이 없으면 새 `HOW_TO_RUN.md` 에 `harness/starter/README-TEMPLATE.md` 틀로). 「된다」 표 칸마다 요구 ID · 코드 경로 · 테스트 이름 · 「안 된다 / 안 했다」 · 환경 변수 이름만 · 대표 수치는 **지금 커밋에서 뽑은 값**.
   - 「AI 활용 기록」 절은 `docs/세션.txt`(역할 수) · `docs/DECISIONS.md`(AI 제안을 바꾼 순간·재작업) · `git log`(위임·시간) 에서 **직접 세어** 5~8줄. 작업 중 따로 쌓는 표는 없다.
   - 루트 README 취급이 「보존」이면 원문을 건드리지 않는다(`git diff` 로 확인). 「교체」(과제가 요구했을 때만)면 원문을 `docs/task/README.md` 로 옮기고 첫 줄에 이동을 적는다.
   - `src/<모듈>/README.md` — 같은 턴에 소유 워커들에게 `[오케→<역할>] 모듈 README — 책임 · 입력→출력 · 테스트 명령, 커밋하고 완료 보고` queue.
   - 공식 답변 파일(`AI_COLLABORATION.md` 류 — 「AI 와 어떻게 협업했나」에 **참가자 본인이** 답하는 제출 양식, 과제설정 2절에 없으면 이 줄은 없다) — M3 부터 모아 둔 **초안**을 커밋하고 `[오케→설명] 공식 답변 초안 사실 확인 부탁 — <경로>` queue. **사실 확인은 설명 탭이 사용자와 하고 파일도 설명 탭이 고쳐 커밋한다**(사용자가 실제로 한 판단만, AI 작업과 구분). 오케는 사용자에게 `다음 입력(설명 탭): 공식 답변 사실 확인에 답해 주세요` 한 줄만 낸다. **M5 전에 시작하지 않는다**(M3·M4 중에는 초안만 모은다). 초안을 최종이라 부르지 않는다.
   모듈 README 가 오면 커밋해 **점검 기준 커밋을 고정한다(동결)** — 해시를 `docs/VERIFICATION.md` 에 적는다. 공식 답변 파일은 사실 확인 중이라 점검 서브에게 「초안 — 형식·존재만 본다」고 알린다. 점검 중에는 제품을 바꾸지 않는다.
5. **점검 3종을 병렬로**(같은 기준 커밋·같은 입력. 메모리 16GB — 띄우기 전 `free -h` 로 여유를 보고, 모자라면 순서대로 돌리고 사용자에게 한 줄):
   - 보안: `.agents/skills/security/SKILL.md` → `docs/security/M5.md`
   - 평가(블라인드 — 제작 맥락을 물려받지 않은 새 세션): `.agents/skills/evaluate/SKILL.md` → `docs/judge/평가-<HHMM>.md`
   - 제출 점검(클린 재현 · 전체 테스트 포함): `.agents/skills/submit/SKILL.md` → `docs/judge/점검-<HHMM>.md`. 기본은 서브에이전트. **사용자가 「제출 점검은 탭으로」라고 했으면** 서브를 띄우지 않고 `다음 입력(새 탭): 탭 이름 제출점검 → codex → /permissions Full Access → /model → 붙이기: 「AGENTS.md 와 .agents/skills/submit/SKILL.md 를 읽고 기준 커밋 <해시> 의 제출 점검 탭으로 시작해」` 한 줄을 낸다. 결과는 queue 로 온다.
   그동안 「검증된 것 / 안 되는 것 / 알고 제출하는 한계」 브리핑 초안을 쓰고, 다 쓰면 `wait_agent` 를 **긴 timeout 한 번** 걸어 서브 결과를 받는다(탭 결과는 queue · 사용자가 「끝났어?」라고 칠 때까지 기다리지 않는다). 하나 올 때마다 한 줄.

## 점검 결과 처리 → 서술형 연습 → 제출
1. 세 결과 문서를 **직접 열어** 지적마다 검산한다(전면 수용 금지, 처분은 `$decision`).
2. **치명적인 것부터**: 제출 실패(필수 파일명·원문 훼손·실행 불가) → 틀린 결과 숫자 → 시크릿·외부 전송 → 안내가 실물과 다름. 수정은 소유 워커에 queue. 기능 추가 금지. 동결 뒤 수정은 기준 커밋·영향 범위를 적고 **영향받은 검사만 다시 돈다** — 옛 PASS 를 새 커밋에 승계하지 않는다. 못 고친 것은 「안 된다」에 쓰고 `$decision`. `$submit` 의 청소 목록은 오케가 지운다(과제 원본 제외) — 지웠으면 제품이 바뀐 것으로 보고 3 의 재확인을 한다.
3. **점검 뒤 제품이 바뀌었을 때만**: 평가 서브에이전트를 한 번 더(evaluate 2단계, `git diff` 로 바뀐 부분만) · 재확인(통합 워커가 돌려 출력을 붙인다) — `harness/verify.sh "<전체 테스트 명령>"` PASS · `python3 harness/tools/evidence_check.py <실행 안내 파일>` 0 · `python3 harness/tools/security_check.py` 0. 바뀐 것이 없으면 submit 서브의 전체 테스트·클린 재현이 그 증거다.
4. 공식 답변 파일이 있으면 설명 탭의 `[설명→오케] 공식 답변 사실 확인 끝 — <해시>` 를 확인한다(안 왔으면 사용자에게 한 줄). 설명 탭이 열려 있으면 `[오케→설명] final 전 서술형 커밋` 을 queue 하고 `[설명→오케] 서술형 커밋 <해시>` 를 확인한다. PLAN 「시간 기준선」 · 점검 보고서 · 세션.txt · VERIFICATION.md · `docs/verify-logs/` 를 **먼저 커밋**(`docs/서술형.md` 는 설명 탭이 자기 커밋으로)한 뒤 `final` 태그 커밋 → `git status --porcelain` 에서 **제출 대상 경로**에 미커밋이 없는 것을 확인(사용자 `메모.md`·ignored 는 예외, 다른 탭의 staged 는 함께 커밋하지 않는다). 이후 `메모.md` 외에 아무 파일도 쓰지 않는다(설명 탭의 서술형 연습도 채팅으로만).
5. 사용자에게 **「검증된 것 / 안 되는 것 / 알고 제출하는 한계」** 를 짧게. 확인을 사용자에게 떠넘기지 않는다. 마지막 두 줄은 고정: 「남은 시간에 설명 탭에서 서술형 연습을 해도 됩니다. 끝나면 화면에서 제출 버튼을 누르세요.」 · 「제출 뒤에는 이 세션으로 돌아오지 않습니다 — 서술형은 직접 타이핑합니다.」 **제출 뒤 보고를 요구하지 않는다**(「제출 완료라고 알려주세요」 류 금지).
6. 사용자가 화면에서 「제출하고 문제풀기」 → 확정. 제출 버튼은 에이전트가 누르지 않는다. 후속 서술형 시작 뒤에는 어떤 탭도 답을 돕지 않는다.
