# M1 — 과제설정 (오케) · 이어서 `M1-실무자대화.md`

## M1 핵심 4줄
- 목표: 이번 과제의 값을 `docs/과제설정.md` 에 고정하고, 실무자 대화를 열어 문제를 확정한다
- 종료 조건: DM 종료 브리핑 → 사용자 「확정」 → `[DM→오케] 문제 확정` queue
- 담당: 오케 (「DM 시작하자」 뒤 M1 동안 PROBLEM 은 DM 소유)
- 증거: `config` 커밋(과제설정 1~6절 · PROBLEM 첫판) · 채팅 보고 · `define` 커밋

## 「과제 시작하자」 — 원문 전부 → 과제설정 → PROBLEM 첫판 → 채팅 보고
이 턴에 쓰는 파일은 `docs/과제설정.md` 와 `docs/PROBLEM.md` 첫판 둘이다. 채팅 보고는 이 두 파일의 요약이다 — 설명 탭은 채팅을 못 보고 파일만 읽으므로, 채팅에만 있는 내용을 만들지 않는다. 새 서브에이전트는 띄우지 않는다(데이터 서브에이전트는 세팅 때 띄웠다).

**역할 나눔**: 오케의 채팅 보고는 결정 재료(요구 · 원문이 말하지 않은 것 · 데이터 · 인프라 · 유형)만 낸다. 과제 상황을 쉬운 말로 풀어 주고 사용자의 이해 질문을 받는 것은 설명 탭 몫이다 — 오케는 상황 해설을 쓰지 않는다.

**읽기 (README 만이 아니다)**: 과제설정 1절 표의 문서 전부 — 과제 `README.md` · 출력 계약(`EXPORT_SCHEMA.md` 류) · 데이터 설명(`data/README.md` 류) · 제출 양식 파일(`AI_COLLABORATION.md` 류) · 과제가 준 AGENTS 절 · 그 밖에 표에 있는 문서(코드·이미지·바이너리는 무엇인지만 확인). 파일이 많아 한 줄로 묶인 폴더는 `ls` 로 안을 보고 문서가 있으면 읽는다. 데이터 파일은 `docs/research/데이터.md` 가 있으면 그것을 읽고, 그 「실무자에게 확인할 것」을 PROBLEM 첫판 7절 해당 주제 아래에 `[데이터]` 태그로 넣는다(그러면 DM 에 따로 queue 하지 않는다). **아직 없으면 직접 프로파일하지 않는다**(서브에이전트와 같은 일을 두 번 하지 않는다) — 데이터 설명 파일만 읽고, 데이터 지도 줄은 「데이터 서브에이전트 진행 중 — 결과는 DM 시작 뒤 DM 쪽으로」로 둔다. 내용을 대화로 세지 않는다. 마지막에 `docs/PROBLEM-TYPES.md`(카드 12개)를 읽어 유형 후보 1~2개를 고른다 — 신호(①)와 결정 변수로 가른다. 맞는 카드가 없으면 억지로 고르지 않고 「맞는 카드 없음」으로 둔다.

**과제설정 채우기 (1~6절, 모든 줄에 근거)**:
- 1절 파일마다 역할·취급(기본 보존 / 과제가 채우라는 양식만 채움 / 참고). 2절 **루트 README 취급** — 기본 보존, 과제가 교체를 요구할 때만 교체. 실행 안내·공식 답변·출력 계약 파일 이름과 양식 위치. 필수 산출물은 이름만 포인터와 함께 나열한다(표 복사 금지).
- 3절 인프라 요구 표 — 로그인·역할·DB 영속·컨테이너·헬스·환경변수·데이터셋 선택/검증·내보내기 방식·포트·제품 안 AI. 하나라도 「예」면 설계 때 담당·검사가 붙어야 한다(「화면+CSV」로 보였던 과제가 인증+DB+Docker 였던 적이 있다).
- 4절 시간 — 시작·제한·종료를 공지 근거로. setup.sh 는 종료 시각을 받지 못하면 기본값 22:00 으로 기준선을 계산해 둔다. **원문·화면 남은 시간·사용자 말과 다르면 4절을 고치고 PLAN 「시간 기준선」을 재계산한다.** 5절 금지·보호. 6절 데이터 묶음(「데이터셋」의 정의, 준비해야 하는 변형 데이터).
- 비어 있으면 「미확인」. 기본값을 지어내지 않는다.

**PROBLEM 첫판 쓰기** — **`docs/PROBLEM.md` 첫판을 1회 쓴다**(0~7절 틀). 원문·데이터에서 나온 내용을 옮기고, 모든 줄에 출처 태그(`[README:줄]` `[<파일>:줄]` `[사용자]` `[짐작]`). 모르는 것은 7절 「미확인」에 적는다. 7절은 **주제 5개 소제목** 아래 확인할 것을 **전부** 적는다 — ① 일의 흐름과 최근 에피소드 ② 걸린 사람과 결과를 받아 하는 일 ③ 업무 규칙과 데이터 이상 처리(단위 · 중복 · 시간대·야간 날짜 기준 · 제외 대상 · 분류 기준 · 빈 값/누락 의미 · AI 사용/외부 전송 · 개인정보 · **규칙이 사람마다 다를 수 있는 것** — 특정 시기·구간에 몰릴 때 · 계획과 다르게 행동한 건 · 상한을 넘는 건을 제외하나 포함하나 · 자원이 남아돌 때 — 이 과제의 말로 바꿔 적는다) ④ 성공 기준 숫자와 측정처 · **결과를 사람이 받아들일 기준**(상한·허용 범위·자원 공급은 사실인가 체감인가) ⑤ 범위 동의(MUST · 안 할 것)와 서면 합의.

둘 다 쓰면 `git add docs/과제설정.md docs/PROBLEM.md` 커밋 `config: 과제설정 · PROBLEM 첫판`.

**채팅 보고** (위 두 파일의 요약 — 원문이 말하지 않은 것은 PROBLEM 7절, 요구는 PROBLEM 3절, 제출 조건은 과제설정 2절):
1. **요구와 제출 조건 표** — 요구 · MUST/선택 · 근거(파일:줄). 출력 계약이 있으면 그 규칙도 요구다. 「~해야」「~할 수 있어야」는 **필수**, 「방식은 자유」「판단에 맡김」은 **선택**. 제출물 배치(과제설정 2절)를 한 줄로.
2. **원문이 말하지 않은 것**(PROBLEM 7절에 적은 것의 요약) — 앞뒤 구간(입력은 어디서, 결과는 누가 받아 다음에 무엇을) · 걸린 사람별 말하지 않은 요구(근거, 없으면 「짐작」) · 모퉁이 너머 터질 문제 2~3개 · **결과 품질을 사람이 받아들일 기준이 비어 있는 곳**(상한·가중치·공급). 인터뷰의 씨앗이라 가장 공들인다.
+ **데이터 지도 한 줄** — 개체(파일) · 이어 주는 키 · 각 파일이 말해 주는 것/말해 주지 못하는 것 · 눈에 띄는 이상(건수). `docs/research/데이터.md` 「구조 한 장」이 ARCHITECTURE 3절이 된다. 「실무자에게 확인할 것」은 첫판 전에 왔으면 7절에 들어가 있고, 뒤에 오면 `M1-실무자대화.md` ① 로 DM 에 queue 한다.
+ **인프라 한 줄** — 과제설정 3절에서 「예」인 것.
+ **유형 후보 한 줄** — 「<유형 이름>(+ <유형 이름>)으로 보인다. 이 유형에서 실무자에게 꼭 묻는 것 · 자주 터지는 예외」(재료는 카드 ⑥·⑤ — 보고에는 유형 이름만 쓰고 카드 번호·내용은 설명하지 않는다). 맞는 카드가 없으면 「맞는 카드 없음」 한 줄. **해법 이름은 말하지 않는다** — 인터뷰 전에 방향을 박으면 실무자 말을 그 틀로만 듣는다. 「후보이고 DM 에서 바뀔 수 있다」를 붙인다. 이 줄이 PROBLEM 7절 ③·④ 의 씨앗이다.

끝에 「실무자 대화 전 첫판이라 대화하며 바뀐다 · 쉬운 설명은 설명 탭에」라고 말한다. 사용자 답 전에 구현하지 않는다. 마지막 줄 `다음 입력(오케): (궁금한 것 자유롭게 · 준비되면 「DM 시작하자」)`.

다음 신호 「DM 시작하자」 → `M1-실무자대화.md`.
