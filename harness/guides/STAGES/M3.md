# M3 — 구현 설계: 설계 논의 · 빈틈 훑기 · 스캐폴드 · 브리프 (오케)

## 핵심 4줄
- 목표: 확정한 솔루션을 **어떤 구조로 · 어느 부분이 어떤 문제를 풀어 · 누가 만드나**로 옮기고(데이터·화면·보안·유지보수·비용·작업 계획까지), 워커가 일만 하면 되게 설계를 끝낸다. 실무자에게 묻지 않고 우리가 정한다
- 종료 조건: 「설계 OK」 뒤 — ARCHITECTURE·PLAN 이 차 있고, 계약 테스트가 빨강으로 돌고, 브리프가 커밋돼 있고, 워커 탭이 전부 「준비됨」이다
- 담당: 오케 (스캐폴드는 서브에이전트)
- 증거: ARCHITECTURE · PLAN · DECISIONS · `docs/brief/<역할>.md` · `tests/contract/` 빨강 출력 · `design` 커밋

사용자가 치는 신호: 「설계 논의하자」(시작 — 솔루션 DM 이 도는 동안 오케가 물어 이미 시작했거나, 솔루션 확정 뒤 오케가 이어서 시작했으면 생략) · 「설계 OK」(설계 브리핑 뒤). 그 사이는 오케와 대화로 정한다. `M2.md` 솔루션 DM 이 도는 동안 먼저 시작해도 된다 — 단 스캐폴드·브리프 커밋과 탭 안내는 `solution` 커밋 뒤에 한다.

## 설계 논의 — 점검표의 구조 쪽을 하나씩 사용자와 정한다
이 표가 논의 순서이자 문서 위치이자 설계 브리핑의 뒷부분이다(세 번 같은 표). 번호는 점검표 ①~⑫ 그대로다 — ①②③⑤⑪ 은 `M2.md` 「솔루션 논의」에서 정했다.

| # | 항목 | 정하는 것 | 적는 곳 |
|---|---|---|---|
| ④ | 구조 | 부분(모듈) 2~4개와 나눈 이유 · **부분마다 어떤 문제를 푸나** · 입력→출력 실제 데이터 모양 · 엔진 흐름(입력→기준안→후보→조건 검사→점수→출력) | ARCH 0·2절 · SOLUTION 3절 |
| ⑥ | 데이터 | 데이터 지도(구조 한 장) · `profile.py` 의 assert 를 데이터셋 검증 규칙으로 · 정리 규칙은 한 곳 · 의미를 바꾸는 보정 없음 | ARCH 3절 |
| ⑦ | 화면·사용 흐름 | **화면 설계 — 아래 「화면 설계」 절의 산출물 셋**(화면 목록 · 화면별 부품 배치표 · 화면 안내 단계 목록)과 같이 정할 것 다섯 · 스타터 페이지(데이터셋/실행/그래프/내 정보) 중 켤 것 · `harness/guides/DESIGN.md` | ARCH 1절 · ARCH 2절(엔진 출력 계약) · 화면·코어 브리프 |
| ⑧ | 로그인·보안 | 역할 분리(과제설정 3절 — 스타터 로그인 껍데기를 켜나) · 빠른 로그인(`AUTH_QUICK`)을 켤지 — 화면 브리프에 적는다 · 서버 측 권한 검사 · 비밀값은 `.env` 에만 · 원본 데이터는 읽기 전용 · 누가 무엇을 조회·실행·결정했는지 기록을 어디에 남기나 | ARCH 5절 |
| ⑨ | 유지보수 | 실무자가 정해 주지 않은 수치(상한·가중치·투입 수)는 코드에 박지 않고 설정값 + 기본값 + 바꿀 때 영향(실제 값은 M4 코어의 민감도 행) · 규칙 파일 위치 · DB 영속 · Docker(스타터 `Dockerfile`·`.dockerignore` 를 루트에 복사하나) · 환경변수 | PLAN 2절 「가정」 행 · ARCH 3·6절 |
| ⑩ | 비용 | 실행 시간·메모리 · 필요 자원 수 · AI 호출 수와 폴백 · 구현 시간 대 남은 시간 | SOLUTION 5절 · PLAN 4절 |
| ⑫ | 작업 계획 | 재사용 재료와 둘 곳 · 워커 N개 · 순서·병렬·자를 순서 · 테스트(계약·경계값·E2E 이름) | PLAN 3~5절 |

진행:
- 항목마다 오케가 「무엇을 정하나(쉬운 말) · 근거(갈래 파일·데이터) · 선택지와 추천」을 내고 사용자와 대화한다. 서로 기대지 않는 항목은 한 응답에 묶어도 된다. 사용자가 고를 것(제품 가치 · 범위 · 우선순위 · 받아들일 한계)은 `harness/roles/DM.md` 「결정을 물을 때」 꼴로 묻고, 기술 선택은 오케가 추천해 사용자가 맡기면 위임으로 기록한다. 용어는 그 자리에서 풀고 우리 데이터 예시를 붙인다. 사용자가 「나머지는 추천대로」라고 하면 남은 항목을 한 번에 채워 브리핑 표로 보인다.
- **결정이 닫힐 때마다** `$decision`(채택·기각 이유 · 근거 파일 · 제안자) 하고 그 항목의 「적는 곳」에 바로 적는다 — 끝에 한꺼번에 쓰지 않는다.
- **킥을 설계에 넣는다** — M2 에서 고른 킥(SOLUTION 0절)이 문서 한 줄로 끝나지 않게: 그 카드의 `화면 한 장` · `지표 3` 을 ⑦ 화면 설계 배치표에(킥 지표가 놓일 화면·부품), 킥이 바꾼 판정 기준을 ARCHITECTURE 4절에, 킥 지표를 PLAN 5절 품질 비교표의 열로 넣는다. 원 분야와 맞지 않는 점은 화면이나 실행 안내 「안 된다」에 한 줄.
- **플러스 알파 논의** — 과제가 요구하지 않았지만 넣을 만한 것(예: 과제 데이터는 읽기만 하고 판정 요청마다 기록을 남기는 것 — `harness/approaches/` 카드에서 고른다)을 넣을지 · 넣는다면 어느 부분에 넣을지 사용자와 정한다. MUST 를 다 채우는 계획이 선 뒤에만 넣고, 넣은 이유를 `$decision` 으로 남긴다.
- **「만약」 세 가지를 뽑는다** — 같은 걸 여러 번 다시 돌리면(재시도 반복) · 운영 조건을 바꾸면 · 이상한 입력이 들어오면. 각각 이 설계에서 어떻게 되고 어떻게 대처하는지를 정해 ARCHITECTURE 5절 **「만약 ①②③」 세 행**과 `docs/서술형-대비.md` 3번 칸에 적는다(세 행이 비어 있으면 설계 브리핑을 내지 않는다). 실제로 돌려 보는 것은 `M4.md` 검증 워커 몫이다.
- 설계 중에 **실무자만 답할 수 있는 업무 가정**(예외·상한·제외 대상)이 새로 나오면 `[오케→DM] M3 확인 질문: <한 토막>` — DM 이 한 질문만 짧게 보낸다(`harness/roles/DM.md` 「확인 질문」). 기다리지 않고 기본값으로 계속 가고 PLAN 2절 「가정」 행에 적는다.
- ⑫까지 돌면 **`$grilling` 빈틈 훑기** — 점검표에서 아직 안 닫힌 것 · 말 없이 가정한 것 · 앞 결정이 바뀌어 다시 열린 것만 1~2라운드 묻는다. 없으면 「빈틈 없음」 한 줄로 넘어간다. **설계 브리핑 끝에 두 줄을 고정으로 붙인다** — `만약 세 가지: ①… ②… ③… (ARCHITECTURE 5절)` · `빈틈 훑기: <물은 것 N개와 정한 것> 또는 「빈틈 없음」`. 이 두 줄이 없으면 사용자는 「설계 OK」를 치지 않는다.

## 화면 설계 — 점검표 ⑦, 산출물 셋을 ARCHITECTURE 1절에 남긴다
화면이 있는 과제면 건너뛰지 않는다. 하는 일이 다르면 화면을 나눈다 — 한 화면에 밀어 넣지 않는다. 고르는 기준의 정본은 `harness/guides/DESIGN-부품.md`(오케는 이 파일만 읽는다 — `DESIGN.md` 본문은 화면 워커 몫), 카탈로그는 `#/widgets`(메뉴에 없다 — 주소로 연다), 배선은 `harness/starter/shadcn/INTEGRATION-화면.md` — **오케는 「화면 더하기·빼기」 절만 읽는다**(오케가 정하는 것은 어느 부품을 어느 화면에 놓나까지다. 붙이는 법 — 「화면 안내」「검토 부품 연결」「결정 부품 연결」「화면 틀이 이미 해 주는 것」 — 은 화면 워커가 읽는다).

0. **핵심 장면 하나를 먼저 정한다** — 이 서비스에서 한 장면만 보여 준다면: **누가 · 무엇을 보고 · 어떤 결정을 내리는 순간인가** 한 문장(PROBLEM 0절의 곤란한 순간이 풀리는 자리 · 킥이 보이는 자리면 더 좋다). 사용자와 정해 ARCHITECTURE 1절 맨 위에 적는다. 아래 화면 목록·배치표·화면 안내는 이 장면을 중심으로 짠다 — 화면을 줄여야 할 때 이 장면에 닿지 않는 것부터 뺀다.

1. **화면 목록** — 왼쪽 메뉴가 될 화면들(순서·묶음)과 역할별 첫 화면(`HOME_BY_ROLE`) · 절차 화면 순서(`src/ui/src/App.tsx` `FLOW`). 이 목록을 `src/ui/src/lib/pages.ts` 의 `SCREENS` 에 한 줄씩 그대로 옮기면 주소·탭 제목·메뉴·도움말·검색이 같이 생긴다(화면 파일은 `src/ui/src/pages/<key>.tsx`).
2. **화면별 부품 배치표** — 화면 × 그 화면이 답하는 질문 × 쓸 부품 번호(W·U·D·V·R) × 넣을 데이터(어느 모듈의 어느 출력). 결과 화면에는 검토 부품(R1 현재 운영 비교 · R2 가장 나빠지는 건 · R3 뺀 기록), 사람이 확정하는 화면에는 결정 부품(D4 결정 바 · D5 결정 기록 · D1 근거 꼬리표)을 **빠짐없이** 적는다 — 없으면 왜 없는지 한 줄. 결과 행마다 「왜 이 결과인지」(어느 입력 · 어느 규칙)를 보일 칸도 적는다 — 없으면 이유 한 줄. **첫 화면 본문 첫 줄**은 PROBLEM 0절의 한 문장(누가 무엇을 판단하는 도구인지)으로 하고 실행 안내 첫 줄과 같게 한다.
3. **화면 안내(온보딩) 단계 목록** — 처음 들어온 사람이 무엇부터 보고 어디서 결정하는지 5~7단계(`src/ui/src/lib/tour-steps.ts` 한 파일). 결정하는 자리와 결과 검토 자리는 꼭 넣는다.

같이 정해 화면·코어 브리프에 적는다: 판정 낱말(결정 바 `options`) · 빠른 로그인(`AUTH_QUICK`) · 빠른 등록 버튼(`QUICK`)을 켤지 · 엔진 출력 계약에 `compare · worst · excluded` 를 넣을지(넣으면 `#/run` 「결과 검토」 카드가 자동으로 뜬다 — `src/ui/server/run.mjs` 머리 주석, ARCHITECTURE 2절 인터페이스에 반영) · AI 대화 패널을 켤지(`domain.json` `chat`).

## 문서 마무리 — 사용자 입력 없이
논의 중 적은 칸을 다듬고 빈 칸을 채운다: SOLUTION 5절 비용 칸 · ARCHITECTURE 0~6절(실행 형태는 과제설정 2·3절과 같게, 과제설정 3절 「예」인 인프라마다 담당 모듈과 검사 이름) · PLAN 2~5절(하드 제약 행마다 테스트 이름). 계약 파일의 값 이름(방향·필드·형식)은 계약 테스트 이름에 그대로.

## 설계 브리핑 — 정한 것 정리
**앞 = 어떻게 만드나**: 부분마다 푸는 문제와 나눈 이유 · 데이터가 흐르는 길(입력부터 화면까지) · 워커와 순서. **뒤 = 점검표 ④⑥⑦⑧⑨⑩⑫ 를 표로, 행 생략 없이** — 항목마다 「정함: 요지 · 적은 곳」 또는 「미처리: 이유」(줄여 쓰다 ⑫가 빠지면 사용자는 작업 계획 없이 넘어간다고 느낀다. 사용자는 미처리와 이상한 줄만 짚는다). 사용자가 「모듈 합쳐」「워커 하나 더」 식으로 고치면 반영해 다시 보인다. 서술형이 「왜 이렇게 나눴나 · 부분마다 무슨 책임을 지나 · 처음부터 화면까지 어떻게 흘러가나」를 묻는다. 끝 `다음 입력(오케): 「설계 OK」(또는 정정)`.

## 「설계 OK」 — 스캐폴드 · 브리프 · 빨강 확인 · 탭 안내
1. **스캐폴드 서브에이전트**. 프롬프트 = `docs/ARCHITECTURE.md` 경로 + 폴더 규약(`src/<모듈>/` · `tests/<모듈>/` · `tests/contract/` · `tests/e2e/`) + 「시그니처만 있는 빈 파일 · 모듈당 계약 테스트 1개 이상(PLAN 2절 이름 그대로) · SOLUTION 4절의 경계값 테스트 이름만 · 구현 금지」. 화면 골격(`src/ui/`)은 M1 에 세워 두었다(`M1-실무자대화.md` ②-2) — 없을 때만 같은 서브가 `bash harness/starter/shadcn/make.sh src/ui` 를 돌린다.
2. **기다리는 동안** `docs/brief/<역할>.md` 를 역할마다 쓴다 — 꼴은 `$handoff` 「브리프」 5필드(정본) + `harness/roles/워커/공통.md` 와 자기 역할 파일(`harness/roles/워커/<역할>.md`) 포인터. 워커 수·역할은 점검표 ⑫ 그대로(코어 · 통합 · 검증 · 화면 + 필요하면 서비스).
3. 스캐폴드가 끝나면(`wait_agent` 긴 timeout) 계약 테스트를 **실행해 빨강인 것을 확인**(`harness/verify.sh "<명령>"` → FAIL 이 정상) · `docs/서술형-대비.md` 2번 칸(구조)을 채우고 3번 칸(만약 — ARCHITECTURE 5절 「만약 ①②③」 그대로)이 비어 있으면 같이 채운다 · 스캐폴드 + 브리프 + 그 문서 커밋 → `design` 태그 · PLAN 1절 실제 시각.
4. **탭 안내 한 번에** — 「탭 N개를 켜 주세요」 + 탭마다 한 줄(문장은 `harness/guides/편성.md` 「새 탭 안내」). 끝 `다음 입력(사용자): 탭을 켜고 붙이기 — 그 뒤 칠 것 없음`.
5. 워커는 브리프 파일을 읽고 **바로 시작**한다. `[<역할>→오케] 준비됨 <UUID>` 는 등록 확인이다 — 세션.txt 와 대조만 하고 답하지 않는다. 역할별 할 일은 브리프와 `M4.md`.
6. 모든 워커의 「준비됨」이 오면 `M4 시작` — `docs/HANDOFF.md` 를 지금 기준으로 쓰고 커밋한다(승계하지 않아도 쓴다 — 새 세션이 이어받을 의도 문서가 증거다). 검증 체계 결정은 `docs/DECISIONS.md` D0 에 있다. **여기가 승계 권장 지점**이다. → `M4.md`.
