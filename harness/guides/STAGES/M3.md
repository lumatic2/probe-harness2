# M3 — 구현 · 통합 · 사용자 QA (오케 + 워커)

## 핵심 4줄
- 목표: 솔루션 확정 때 정한 모듈·계약·엣지 대처가 그대로 코드가 되고, 사용자 흐름이 실제 데이터로 한 번 관통해 돌아간다
- 종료 조건: 「QA 끝」 — 사용자가 플랫폼 Browser 로 기능·화면을 보고 지적을 끝냈고, 오케와 끝난 것·안 된 것을 합의했다
- 담당: 코어 워커는 계산, 통합 워커는 서버·E2E·Docker·실행 재현, 화면 워커는 화면과 **사용자 QA 대화**, 오케는 판단·재지시·브리핑
- 증거: 계약 테스트 초록 · E2E · PLAN 5절 「전체 기간」 행 · 사용자 첫 화면 확인 · `build` 커밋

사용자가 치는 것은 QA 지적 · 「구현 끝」(오케 탭) · 「QA 끝」(화면 탭) · 끝 되읽기에 「맞다」 — 그 밖의 결정은 솔루션 확정 때 끝났고, 새로 필요하면 오케가 묻는다.

## 역할 — 몇 개 · 무엇은 M2 에서 정했다
워커 수 · 이름 · 맡는 모듈은 M2 점검표 ⑫ 에서 사용자와 정했고 `docs/brief/<역할>.md` 에 있다. 아래는 어느 과제든 서는 기본 역할의 할 일이다(브리프가 자기 절을 가리킨다). 탭 이름은 역할 이름(코어 · 통합 · 화면 · 서비스), 구현 워커가 모듈을 하나씩 맡으면 모듈 이름.

### 공통 (모든 워커)
- 시작: `AGENTS.md` · `.agents/skills/handoff/SKILL.md` · `docs/brief/<역할>.md` 를 읽고 `docs/세션.txt` 에 등록 → 오케에 `[<역할>→오케] 준비됨 <UUID>` → **기다리지 않고 바로 시작**. 브리프에 적힌 계약 절과 요구 ID 만 만든다. 브리프가 없을 때만 「브리프 대기 중」 한 줄.
- 자기 소유 경로만 쓰고 커밋도 자기 경로만(다른 탭의 staged 파일이 보이면 멈추고 알린다). `tests/contract/` 는 고치지 않는다 — 틀렸다고 보면(출력 계약 파일과 어긋남 포함) 보고한다. 경계값·오류 입력 테스트는 SOLUTION 4절 엣지 표의 행 이름 그대로 3개 이상. 실패는 `.agents/skills/systematic-debugging/SKILL.md` 대로 재현 → 원인 → 최소 수정 → 같은 명령 재통과.
- **보고는 셋뿐 (정본 — handoff·오케.md 는 이 절을 가리킨다)**: ① **완료 1회** — 기준 커밋 · 바뀐 것 · 검증 명령과 출력(`harness/verify.sh "<명령>"` · `python3 harness/tools/security_check.py` — 워커가 직접 돌려 붙인다) · 우려 · 필요한 결정 0~1개 · 「된다」 표 줄(요구 ID → 코드 경로 → 테스트 이름) ② **결정이 필요한 질문**(막힘 · 인터페이스 변경 필요 포함) ③ **새 오류**(보안 · 데이터 손실 위험 포함). 「대기 중」 · 「지시 반영했음」 · 같은 상태의 재보고 · 진행률은 보내지 않는다(오케 턴을 먹는다). 파일에 있는 장문을 다시 보내지 않는다.
- **못 정하는 것은 위로**: 워커 → 오케. 오케가 기술 판단은 정하고, 실무자만 아는 업무 사실은 DM 에, 가치 · 범위 · 받아들일 한계는 사용자에게 올린다(아래 「오케」 절).

### 코어
`src/<모듈>/` 의 순수 계산(HTTP·DB·화면 없이 입력→결과)만. `server/engine.mjs` 의 `runEngine` 은 그 함수를 부르는 얇은 어댑터로 **통합이** 잇는다 — 같은 계산을 두 곳에 두지 않는다. 데이터 과제면 `docs/experiments/profile.py` 의 assert 목록을 완료 보고 「된다」 표에 넘긴다(규칙 파일은 통합이 쓴다). 계약 테스트 초록 → **전량 데이터 1회 실행**(시간·메모리 기록) → PLAN 5절 품질 비교표 「전체 기간」 행(최악 사례 5개 · 개인별 악화 수 · p95/최대 · 자원 · 하드 제약 지킴). **표본과 크게 다르면** 완료 보고 첫 줄에 쓴다 — 「크게」 = ① 풀이 조건표의 상한·필수 조건을 넘는 건이 생겼거나, M2 에서 이 해법을 고른 이유가 뒤집힐 만큼(다른 후보가 이겼을 수준) 최악·악화 수·자원이 달라졌다. **완료 보고 뒤** 결과를 좌우하는 기본값(PLAN 2절 「가정」 행) 1~2개를 앞뒤로 한 번씩 더 돌려 PLAN 5절에 「민감도 <값>」 행을 적는다(전량이 오래 걸리면 표본으로, 표에 밝힌다). 결론이 뒤집히면 「기본값에 민감」으로 보고한다.

### 화면
`harness/guides/DESIGN.md` 먼저. 「OK」 때 스캐폴드 서브가 `make.sh` 로 세운 `src/ui/` 위에서 시작한다(재실행 금지 — 없으면 오케에 보고). ARCHITECTURE 2절 인터페이스로 코어를 기다리지 않고 만든다. 안 쓰는 도메인 견본·AI 데모 라우트·가짜 비밀값은 시작 때 끈다. 서버는 통합이 띄운다 — 빌드가 되는지만 확인하고 `[화면→통합] 빌드됨 <커밋>`. 첫 화면 뒤에는 **사용자 QA 대화 상대**(아래 「사용자 QA」).

### 통합
`harness/guides/BROWSER.md` 대로 빌드 UI + API 단일 서버를 `0.0.0.0:3000` 에(서버 탭 소유). 서버 쪽 문제는 `harness/starter/shadcn/INTEGRATION.md` 「서버 모듈 지도」로 파일을 찾고, `runEngine` 어댑터가 코어를 부르게 잇는다. 다른 워커가 **커밋한 것만** 받아 올리고 그 코드는 고치지 않는다 — 찾은 버그는 소유 워커에게 직접 queue 로 재지시하고 오케에는 결과만.
- 데이터셋 적용 요구가 있으면 코어가 넘긴 assert 목록을 `data/datasets/schema.json` 규칙으로 옮긴다(같은 점검을 두 벌 쓰지 않는다) · 검증 UI 4규칙(오류를 한 번에 전부 · 파일·행·열·값·어긴 규칙 · 구조 오류와 값 오류 분리 · 실패 묶음은 409 로 기존 유지) · E2E 두 줄(잘못된 묶음→409→기존 유지 · 적용 뒤 재생성 알림).
- E2E 1개(ARCHITECTURE 1절 사용자 흐름을 입력부터 결과까지, **HTTP 요청으로** — 브라우저 자동화는 쓸 수 없고 화면 근거는 사용자가 플랫폼 Browser 로 본 것이다) 초록 · 빈 입력 · 깨진 입력 · 초대형 입력 · 날짜 경계를 한 번씩 · **서버를 거쳐 전량 1회** — 코어 「전체 기간」 숫자와 같은가 + 응답 시간·메모리만 적는다(PLAN 행은 코어 것) · Docker·재시작 복구(ARCHITECTURE 5절).
- 화면의 `재빌드 <커밋>` 을 받으면 빌드·재기동 뒤 `[통합→화면] 재기동됨 <커밋>`.
- 첫 화면이 사용자 흐름으로 관통하면 `[통합→오케] 첫 화면 <포트 3000 · 경로 /> · E2E 초록 · 전체 기간 행 있음/진행 중`(진행 중이면 시연 안내의 「아직 안 되는 것」에 넣는다).

### 서비스 (M2 ⑫ 에서 켰을 때만)
API·DB 층 — ARCHITECTURE 2절 서비스 행 그대로. 받고 돌려주기만 하고 계산은 코어. 서버 측 권한 검사(ARCHITECTURE 5절) · 테스트는 임시 DB·합성 계정. 서버에 올리는 것은 통합.

## 오케 — M3 시작 턴
모든 「준비됨」이 오면(M2 「솔루션 확정」 4) 사용자에게 한 줄: `지금 칠 것 없음 — 설명 탭에서 서술형 연습을 해도 됩니다. 첫 화면이 오면 화면 탭에서 QA 합니다(예상 HH:MM).`

## 오케 — 완료 queue 가 올 때마다 (읽고 판단만, 다시 돌리지 않는다)
- 답은 **지시나 결정이 있을 때만**. 워커가 상태 보고를 반복하면 「완료·질문·새 오류 때만 보고」 한 줄로 한 번 바로잡고 그 뒤는 무시한다.
- 본다: 검증 출력이 초록인가 · security_check 0 인가 · 데이터 과제면 `schema.json` 규칙이 assert 목록과 같은 점검인가(두 벌이면 재지시) · **경계** — 코어 모듈이 HTTP·DB 를 import 하지 않는다(`grep -rlE "fastapi|flask|django|starlette|express|node:http|http\.server|sqlite|psycopg|pymysql|mongo" src/<코어>/` 가 비어야 한다) · 「된다」 표 줄이 PLAN 2절 ID 와 맞는가.
- 빠진 것은 같은 UUID 로 **변경점만** 재지시. 통과는 PLAN 3절 상태에 한 줄. 오케가 직접 `harness/verify.sh` 로 재실행하는 것은 **같은 원인 2번 실패 뒤 1회**(`docs/DECISIONS.md` D0) — 같은 원인 2번 실패면 브리프를 고쳐 다시 보낸다.
- **코어 완료를 받은 턴에**, 출력 계약 파일이 있으면 **독립 검산 서브에이전트**를 띄운다 — 프롬프트 = 원본 경로 + 계약 파일 + 「`src/`·`tests/`·`docs/experiments/` 는 읽지 말고 원본에서 기대 집합을 만들어 대조」. 결과는 `docs/VERIFICATION.md` 에, 어긋나면 코어에 재지시.
- 코어 보고에 「표본과 크게 다름」·「기본값에 민감」이 있으면 받아들일 한계가 바뀐 것이라 사용자 몫이다 — 사용자에게 3줄(가장 나쁜 사람 · 악화 규모 · 자원)과 추천(이대로 / 대처 바꾸기) → 사용자가 정하고 `$decision`. 보고의 「결정 필요」가 기술 판단이면 오케가 정한다. **실무자만 답할 수 있는 업무 가정**(예외·상한·제외 대상)이면 `[오케→DM] M3 확인 질문: <한 토막>` — DM 이 한 질문만 짧게 보내고, 답이 오면 `$decision` 뒤 소유 워커에 재지시. 기다리는 동안 워커는 PLAN 2절 「가정」 행의 기본값으로 계속 가고 그 사실을 보고에 적는다.
- 기다리는 동안: 「된다」 표 줄을 실행 안내 파일에 모은다 · FEEDBACK 첫판 재료 · 공식 답변 파일(과제설정 2절) 초안에 **지금까지 사용자가 실제로 한 판단**을 적어 둔다(막판에 몰면 사실 확인을 못 한다).

## 첫 화면 → 사용자 QA · 얇은 결과 시연
화면이 없으면(과제가 파일 출력이거나 npm 이 막혀 안 세웠을 때) 통합이 「첫 화면」 자리에 결과 파일 경로·실행 명령을 보고하고, 아래 화면 워커 몫(시연 안내 · 지적 받기)은 오케가 한다. 「QA 끝」도 오케 탭에 친다.

1. 통합의 「첫 화면」을 받은 턴에 셋: 사용자에게 「화면 탭에서 봅니다 — Browser 포트 칸 `3000` · 경로 칸 `/`」 한 줄 · 화면 워커에 `[오케→화면] 시연 안내 시작 — SOLUTION 3절·「된다」 표·BROWSER.md 로` queue · **얇은 결과 시연** — 핵심 흐름이 실제 데이터로 관통했으니 다른 모듈을 기다리지 않고 `다음 입력(오케): 「피드백 DM 시작하자」 — QA 와 겹쳐 돌아도 됩니다`(`M4-5.md`). 단 전체 기간 행이 진행 중이면 이 안내는 행이 들어온 뒤에 낸다(실무자에게 보일 숫자가 그 행이다). 부분 시연은 미구현 범위를 밝힌다.
2. **화면 워커가 사용자의 QA 상대다.** 먼저 시연 안내 한 덩어리: 포트 `3000` · 경로 `/`(하위 화면은 `/#/list` 식) · 볼 것 3개(어디에 무엇이 실제 값으로 보여야 하나) · 해볼 것 2~3개(입력값 · 행동 · 예상 결과 · 요구 ID) · 로그인 계정 이름(값은 `.env.example`) · 데이터셋 적용 요구가 있으면 「잘못된 묶음 적용 → 오류가 파일·행·열·값·규칙으로 한 번에 전부 보이고 기존 데이터 유지」 하나 · 아직 안 되는 것 · 안 열릴 때 확인 순서(`harness/guides/BROWSER.md`). 마지막 줄 `지적은 「<어디> <어떻게>」로, 다 봤으면 이 탭에 「QA 끝」`.
3. 지적 처리:
   - **화면 지적**(배치·문구·단위·누름 반응)은 화면이 그 자리에서 고쳐 커밋 → `[화면→통합] 재빌드 <커밋>` → 통합의 `재기동됨` 을 받은 **뒤** 사용자에게 「다시 열어 보세요」.
   - **계산·데이터·범위 지적**은 묶어 `[화면→오케] 지적: <어디> <어떻게> ×N` 한 번에 → 오케가 받을지 판단(새 요구면 「요구에 없다」 — 받을지는 사용자에게 묻고 `$decision`) → 소유 워커에 재지시하며 「고치면 화면에 직접 `[<역할>→화면] 반영 <커밋>`」을 붙인다 → 화면이 통합에 재빌드 요청 → 사용자에게. 화면 워커는 코어·서비스 코드를 고치지 않는다.

## 「구현 끝」 — 사용자가 친다 (시각으로 스스로 시작하지 않는다)
모든 워커의 첫 완료를 받으면 오케가 한 번 `다음 입력(오케): 「구현 끝」 — 치면 새 기능을 막습니다` 로 알린다.
살아 있는 워커 전부에 `[오케→전체] 계획한 구현 끝 — 새 기능은 시작하지 말고 지금 것 마무리와 피드백 처분 수정만, 못 한 것은 「안 된다」로` queue. 남은 것을 줄일지는 사용자가 묻거나 정할 때 얇게 / 안 할 것을 함께 고른다(`$decision`).

## 「QA 끝」
사용자가 화면 탭에 「QA 끝」을 치면(오케 탭에 직접 쳐도 같다) 화면 워커가 `[화면→오케] QA 종료 — 지적 N건: 자리에서 처리 n · 오케 이관 m(처리 상태) · 받지 않은 새 요구 k` 를 queue 한다. 오케가 끝난 것 · 안 된 것(실행 안내 「안 된다」에 갈 것) · 남은 지적 처리 상태를 3줄로 되읽고 사용자가 「맞다」 하면 `build` 태그 커밋 → PLAN 1절 실제 시각 → 다음 할 일 한 줄. 중요한 실패가 남아 있으면 완료로 표시하지 않는다.
