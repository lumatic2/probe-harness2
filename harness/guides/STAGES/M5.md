# M5 — 피드백 · 수정 (오케 + DM)

## 핵심 4줄
- 목표: 완성된 결과를 실무자에게 알리고 짚은 것을 처분해 **수용 여부를 한 번 확인**한다
- 종료 조건: 「피드백 끝」 — 실무자가 짚은 것이 전부 처분됐고(반영 · 설득 · 사용자 결정), 독립 재계산 대조가 끝났다
- 담당: DM 탭이 대화, 오케가 처분·수정 지시, 서브에이전트가 독립 재계산
- 증거: `docs/FEEDBACK.md` · `docs/VERIFICATION.md` 독립 재계산 · `feedback` 커밋

경계의 뜻: 「구현 끝」 뒤 새 기능은 시작하지 않고 피드백 처분 수정은 계속 · 「피드백 끝」 뒤 제품 변경은 M6 점검 지적뿐. 시각은 `harness/guides/지도.md` 「시간 기준선」(참고).

## 「피드백 DM 시작하자」
1. `docs/FEEDBACK.md` 첫판. 1절은 실제 데이터로 **먼저 돌린** 숫자와 **품질 비교표 포인터**(PLAN 5절 「전체 기간」 행 — 복사하지 않는다)만. 예정·샘플을 실제로 적지 않는다.

```
# FEEDBACK — 실무자 피드백 (M5, 살아 있는 문서)
> 모든 줄에 출처: [답변N] · [테스트:이름] · [명령:…]. 바뀐 줄은 ~~옛~~ → 새 [답변N].

## 1. 보여 줄 결과
| 성공 기준(PROBLEM 5절) | 기준선 | 지금 숫자 | 측정 명령 | 실무자 반응 |
|---|---|---|---|---|
| 품질 비교표 → `docs/PLAN.md` 5절 「전체 기간」 행(복사하지 않는다) | | | | 실무자 반응은 PLAN 표의 마지막 열에 |

## 2. 피드백 표
| F-ID | 실무자 말(원문 요약) | 분류(아래 처분 표) | 처분과 이유 | 검증(실패 출력 → 같은 명령 재통과) | 다시 알렸나 |
|---|---|---|---|---|---|

## 3. 받지 않은 것과 남은 한계 · 마지막 수용
- (새 요구 — 받지 않은 이유 · 실무자에게 말했나 · 실행 안내 「안 된다」로)
- (결과 불수용이 남은 것 — 사용자 결정 · 원인 · 공급/기준 미확인은 「미확인」으로)
- 마지막 수용: (수용 / 이의 처분 / 검토용으로 쓸 수 있음 — [답변N])
```

2. **DM 탭이 살아 있으면**(`docs/세션.txt`) 오케가 `[오케→DM] 피드백 DM 시작해 — harness/roles/DM.md` 를 queue 하고 사용자에게 `DM 탭에서 피드백 DM 이 시작됩니다` 한 줄만 낸다. 탭이 없을 때만 안내: `DM 탭에 「harness/roles/DM.md 읽고 피드백 DM 시작해」`, 마지막 줄 `다음 입력(DM): harness/roles/DM.md 읽고 피드백 DM 시작해`. DM 이 도는 동안 오케는 DM 에 상태·독촉 queue 를 보내지 않는다 — DM 은 실무자 답이 와야 움직이고, 답은 사용자가 붙인다.
3. 독립 재계산 서브에이전트는 `M4.md` 코어 완료 턴에 이미 띄웠다 — 여기서 다시 띄우지 않는다. 코어 완료 전에 시연을 시작해 아직 안 띄웠으면 지금 띄운다(프롬프트는 `M4.md` 그 줄). 대조는 「피드백 끝」 턴에 한다.

## 처분 — `[DM→오케] M5 답 N` 이 오면 (정본 — DM 파일은 이 표의 「DM 이 전하는 말」만 쓴다)
DM 이 원문을 `docs/interview/M5.md` 에 남기고 문장마다 분류 후보를 붙여 보낸다. **F-ID 와 처분은 오케만** FEEDBACK 2절에 쓴다. 기본은 **설득하고 밀고 간다** — MUST 는 채웠고 가정은 M2 에서 기본값으로 알렸고 이의가 없었다.

| 분류 | 처분 | 누가 정하나 | DM 이 전하는 말 |
|---|---|---|---|
| 버그 · 틀린 숫자 | 고친다 | 오케 | 「반영하겠습니다」 → 고친 뒤 ④ 통에 「지금은 이렇습니다」 |
| 작은 보정(표시·문구·단위 — 결과가 안 바뀜, MUST 안) | 고친다 | 오케 | 위와 같다 |
| 받지 않을 것(새 요구 · 합의와 다른 방향) | 안 고친다 | 오케 · 같은 요청이 두 번이면 사용자(`$decision`) | 세 줄 설득: 「앞서 ○○로 합의했고 → 그 기준에서 이렇게 처리했으며 → 요청대로 바꾸면 ○○(숫자)이 생깁니다. 이번에는 기존 방식으로 가고 ○○는 다음 단계 과제로 적어 두겠습니다.」 근거는 M1·M2 합의 · 데이터 · 시간 안에 되는 것만. 「기술적으로 어렵다」는 쓰지 않는다 |
| 막판 뒤집기(합의와 다른 소리) | 안 고친다 | 오케 · 사용자가 뒤집고 싶을 때만 `$decision` | 「그 부분은 앞서 ○○로 합의한 내용이어서 시간 관계상 기존 방식으로 진행하겠습니다. 의견은 기록해 두겠습니다.」 사용자에게 「뒤집기 왔음 · 기존 방식 유지」 한 줄 |
| 의미를 바꾸는 보정(결측 채우기 · 방향 대칭화 · 평균 대체 · 실적으로 수요 깎기) | 사용자가 정할 때만 정리 뷰 한 곳에서 | 사용자(`$decision`) | 결정대로 |
| 절대 안 된다(출력을 못 쓴다 · 규정 위반 · 필수 누락이 명시적) | 고친다 | 오케 `$decision` | 「반영하겠습니다」 |
| **결과 불수용**(「이 결과는 윗선에 못 올린다」류) | 사용자에게 올린다: 「대안 분석 1회(코어, N분) / 한계로 적고 검토용으로 닫기」 — 재분석을 자동으로 시작하지 않는다 | 사용자(`$decision`) | 결정대로. 「접수」(확인되면 알려 달라)는 수용이 아니다 |

- 고칠 것은 소유 워커에게 같은 UUID 로 **변경점만** 재지시하고, 완료 보고의 검증 출력을 읽어 검수한다(재실행은 `docs/DECISIONS.md` D0). 고쳐지면 `[오케→DM] 반영됨: F<n> <한 줄>` — DM 은 ④ 통에 몰아 전한다.
- 「피드백 끝」 때 남은 수정은 영향과 처리안(얇게 / 「안 된다」로)을 보이고 사용자가 정한다.

## 「피드백 끝」(DM queue) — 이 턴이 M5→M6 경계 턴이다
**두 턴으로 나눠 한다** — 이 턴(「피드백 끝」을 받은 턴)은 0 까지만 하고 끝낸다(첫 줄 `M5 마무리 — 제출 정리 중 (HH:MM)`). 화면 워커의 제출 정리 완료 보고가 온 턴에 첫 줄 `M5 종료 → M6 시작 (HH:MM)` 을 쓰고 1~3 을 한 뒤 바로 `M6.md` 「점검 기준 고정」로 간다. 「구현 끝」을 아직 안 쳤으면 그 queue(`M4.md`)를 이 턴에 보내고, 「QA 끝」이 아직이면 사용자에게 「QA 를 여기서 마칠까요」 한 줄을 묻는다 — 마치면 `M4.md` 「QA 끝」 되읽기와 `build` 커밋을 먼저 한다.
0. **제출 정리(점검 기준 고정 전에 끝낸다 — 점검 기준 고정 뒤에 지우면 재확인이 한 바퀴 더 돈다)**: ① `[오케→화면] 제출 정리` queue — 개발 메뉴 끄기 · 안 쓰는 화면·견본 빼기 · 화면 안내 확인 · 재빌드(`harness/roles/워커/화면.md` 「제출 정리」) ② 오케가 안 쓴 참고 문서를 지운다 — `harness/approaches/`·`harness/methods/` 에서 `docs/` 와 `src/` 가 가리키는 것만 남긴다(기준과 명령은 `.agents/skills/submit/SKILL.md` 4-0). 발표자료 틀 `harness/pitch/` 도 같이 본다 — 사용자가 발표자료를 시키지 않았으면(`grep -c "⟨NAME⟩" harness/pitch/deck/index.html` 이 1 이상 = 안 채운 틀) 통째로 지우고, 채웠거나 사용자가 남기라고 했으면 그대로 둔다 ③ 「구현 끝」 때 요청한 모듈 README 가 다 왔는지 본다(안 온 것만 재요청). 화면 워커가 없으면(화면 없는 과제 · `docs/세션.txt` 에 살아 있는 화면 줄 없음) ① 을 건너뛰고 턴을 끝내지 않은 채 바로 1 로 간다. 있으면 여기서 턴을 끝내되(이 턴 끝에는 「M5 종료 조건 충족」 줄을 쓰지 않는다 — 둘째 턴에 쓴다) 마지막 줄을 고정한다 — `다음 입력(오케): 칠 것 없음 — 화면 탭의 제출 정리 보고가 오면 이어집니다. 3분 넘게 조용하면 「이어가」`. 화면 워커의 완료 보고가 오거나 「이어가」를 받으면 1 로 간다(「이어가」면 화면 탭 상태를 한 줄로 알리고, 남은 정리는 M6 점검 지적으로 처리한다).
1. **독립 재계산 대조**: 기대값과 지금 커밋의 제품 숫자를 맞춘다(아직 안 왔으면 `wait_agent` 긴 timeout). `docs/VERIFICATION.md` 에 일치/불일치 · 기준 커밋. 불일치는 틀린 숫자로 처분한다. 대조 결과는 `docs/서술형-대비.md` 6번 칸에도 적는다.
2. `feedback` 태그 커밋 · PLAN 「시간 기준선」 실제 시각. 이 뒤로 제품 변경은 M6 점검 지적뿐이다.
3. 끝난 것 한 줄 · 다음 할 일 한 줄. 구현 탭은 모듈 README·점검 지적 수정이 오므로 `final` 까지 둔다.
