# M2 — 문제 확정 · 조사 · 솔루션 설계 · 솔루션 확정 (오케)

## 핵심 4줄
- 목표: 합의된 문제를 **무엇을 만들어 · 어떤 구조로 · 어느 부분이 어떤 문제를 풀어** 해결할지 조사 근거 위에서 사용자와 정하고(튀는 경우·보안·유지보수·비용·기대효과까지), 워커가 일만 하면 되게 설계를 끝낸다
- 종료 조건: 「솔루션 확정」 — 실무자가 솔루션 설명을 듣고 반응했고(푼다 / 빠진 것은 사용자 결정으로 처분), SOLUTION·ARCHITECTURE·PLAN 이 차 있고, 계약 테스트가 빨강으로 돌고, 브리프가 커밋돼 있다
- 담당: 오케 (조사·시험 적용·스캐폴드는 서브에이전트, 실무자 반응은 DM 탭)
- 증거: `define`·`solution` 커밋 · `docs/research/<갈래>.md` · SOLUTION · ARCHITECTURE · PLAN · DECISIONS · `tests/contract/` 빨강 출력

사용자가 치는 신호: 「돌려」(조사 갈래 합의 뒤) · 「설계 논의하자」(조사 설명 뒤) · 「OK」(솔루션 브리핑 뒤) · 「확정」(DM 탭). 그 사이는 오케와 대화로 정한다.

## 「문제 확정」 — 같은 턴에 조사 논의까지
DM 이 종료 브리핑을 하고 사용자가 「확정」을 치면 DM 이 `[DM→오케] 문제 확정` 을 queue 한다(사용자가 직접 쳐도 같다). 문제 설명·4조건 판정·점검기는 DM 이 끝냈다 — 다시 하지 않는다. `docs/PROBLEM.md` 를 한 번 읽고:
1. 5절 `[사용자 결정]` 을 `$decision` 으로 옮긴다.
2. PROBLEM 확정 시각을 적고 `define` 태그 커밋 · PLAN 1절 실제 시각. 이 뒤로 PROBLEM 은 확정판이다 — M2 의 결정은 DECISIONS·SOLUTION 에 쓴다.
3. **같은 응답에** 아래 「조사 논의」 1 의 갈래안을 낸다(신호를 한 번 더 받지 않는다).
4. 끝 두 줄: `다음 입력(오케): 「돌려」(또는 갈래·조사처·깊이 고치기)` · `솔루션 논의 전에 오케를 새 세션으로 바꾸려면 「승계하자」 — 갈래안은 HANDOFF 로 넘어간다(새 탭 모델·effort 는 사용자가 고른다)`.

## 조사 논의 — 어디를, 얼마나 찾을지 사용자와 정한다
조사는 솔루션을 고를 재료를 밖에서 모으는 일이다 — 같은 문제를 푼 사례와 그들의 선택 · 표준 해법과 한계 · 재사용할 코드와 데이터 처리 선례 · 현장 규정. 모델 지식만으로 고르지 않는다.
1. 오케가 **갈래 3~4개**를 제안한다. 갈래마다 한 줄: 「질문 · 답을 알면 솔루션 선택이 어떻게 달라지나 · 어디를 찾나(`harness/roles/리서치.md` 「어디를 찾나」 표에서 1~2곳) · 깊이(원문 몇 개 · 언제 멈추나) · 산출 `docs/research/<갈래>.md`」. 이어서 서브 수(= 갈래 수)와 예상 소요, **쓸 조사 도구** — 기본은 Codex 웹 검색이고, 그 밖의 도구는 `command -v <이름>` 으로 이 환경에 있는지 본 뒤 있을 때만 제안한다(예: 국내 블로그·지식iN 검색 CLI). 갈래는 M1 유형 후보(과제 시작 보고 · PROBLEM 7절)에서 출발하고, 후보가 없으면 PROBLEM 에서 출발한다. `docs/PROBLEM-TYPES.md` 카드는 사용자에게 설명하지 않는다. 문제·제약 설명은 되풀이하지 않는다.
2. 사용자가 갈래·조사처·깊이·도구를 고치면 반영해 다시 보인다. 「돌려」를 받으면 갈래마다 서브에이전트 하나. 프롬프트 = `harness/roles/리서치.md` 전문 + `docs/PROBLEM.md` 경로 + 그 갈래 한 줄 그대로.
3. **도는 동안** 오케는 사용자 입력 없이 ① PLAN 2절 추적 표를 채운다(M1 에 옮긴 요구 R 행에 수치 제약 C · 성공 기준 G · 제출 제약 S 를 더한다) ② `docs/SOLUTION.md` 0절 **풀이 조건표** 초안을 쓴다(아래 점검표 ①의 재료). 사용자는 설명 탭에서 공부하면 된다 — 오케 탭에 칠 것은 없다.
4. 다 쓰면 `wait_agent` 를 **긴 timeout 한 번**(300000ms) 건다. 기다리는 동안 오케 탭은 답하지 않는다(사용자가 치면 쌓였다가 처리된다). 갈래가 끝날 때마다 한 줄. timeout 이 지났는데 남은 갈래가 있으면 `N/M 도착 — 다시 기다림` 한 줄 찍고 다시 건다. 예상 소요의 두 배를 넘으면 사용자에게 「더 기다림 / 온 것으로 진행」을 묻는다.

## 조사 설명 — 결정 없이, 이해시킨다
갈래가 다 오면 파일을 전부 읽는다(중간 요약 문서는 만들지 않는다 — SOLUTION 이 갈래 파일을 가리킨다). 사용자에게 **가르치듯** 설명한다 — 설계 논의에서 스스로 고를 수 있을 만큼. 순서: ① 이 문제가 어떤 종류인가(교과서 이름 + 쉬운 뜻 한 문장) ② 사례 2~3개(누가 · 어떤 상황 · 왜 · 무엇을 골랐고 결과) ③ 우리 상황·제약과 같은 점·다른 점 ④ 해법 선택지 1~N — 각각 뜻 한 문장 · 우리 데이터로 보면 어떤가 · 장단점 ⑤ 자주 터지는 예외와 현장의 처리 ⑥ 가져다 쓸 재료 ⑦ 못 찾은 것·상충. 결론·표만 던지지 않는다. 길어도 된다. 이 응답에서는 결정을 묻지 않는다. 끝 `다음 입력(오케): 궁금한 것 자유롭게 — 다 이해했으면 「설계 논의하자」`.

## 설계 논의 — 점검표를 하나씩 사용자와 정한다
이 표가 논의 순서이자 문서 위치이자 솔루션 브리핑의 뒷부분이다(세 번 같은 표).

진행:
- 항목마다 오케가 「무엇을 정하나(쉬운 말) · 근거(갈래 파일·데이터) · 선택지와 추천」을 내고 사용자와 대화한다. 서로 기대지 않는 항목은 한 응답에 묶어도 된다. 사용자가 고를 것(제품 가치 · 범위 · 우선순위 · 받아들일 한계)은 `harness/roles/DM.md` 「결정을 물을 때」 꼴로 묻고, 기술 선택은 오케가 추천해 사용자가 맡기면 위임으로 기록한다. 용어는 그 자리에서 풀고 우리 데이터 예시를 붙인다. 사용자가 「나머지는 추천대로」라고 하면 남은 항목을 한 번에 채워 브리핑 표로 보인다.
- **결정이 닫힐 때마다** `$decision`(채택·기각 이유 · 근거 파일 · 제안자) 하고 그 항목의 「적는 곳」에 바로 적는다 — 끝에 한꺼번에 쓰지 않는다.
- **정답이 없는 과제면 ①이 답을 정한다** — 「맞는 답」을 찾지 않고, ①의 기준 순서로 이기는 안을 고른다. 그래서 **①이 닫히기 전에는 후보 비교·시험 적용을 하지 않는다**(기준 없이 비교하면 결과마다 기준이 흔들려 실험이 되풀이된다).
- **해봐야 아는 것 → 시험 적용**(①이 닫힌 뒤, ③ 해법 고르기나 ⑤ 튀는 경우에서 데이터를 돌려 봐야 고를 수 있을 때): 해법 후보를 데이터 일부(하루치 등 — 「표본」)에 돌려 보는 일회성 서브에이전트. 꼴은 고정이다 — ⓐ 비교 대상은 항상 **지금 방식(기준안) + 후보 1~2개**(기준안이 없으면 「나아졌나」를 말할 수 없다) ⓑ 띄우기 전에 「무엇이 나오면 무엇을 고르나」 한 줄 ⓒ 결과 = 최악 사례 5개 · 개인별 악화 수 · p95/최대 · 자원을 뽑는 스크립트(`docs/experiments/`, 구현 아님) → PLAN 5절 「표본」 행, ①의 기준 순서대로 한 표. `wait_agent` 긴 timeout 으로 기다린다. 사용자에게 3줄(가장 나쁜 사람 · 악화 규모 · 자원)과 추천으로 보이고 고른다.
- **그래도 판가름이 안 나면 다시 돌리지 않고 정한다** — 더 단순하고 검산하기 쉬운 안을 고르고, 갈리는 값은 설정값으로 열어 두고, 확인은 M3 전량 실행(코어 「표본과 크게 다르면 보고 첫 줄」)으로 넘긴다. 다시 돌리고 싶으면 먼저 사용자에게 「한 번 더 vs 지금 것 중 고르기」를 묻는다.
- ⑫까지 돌면 **`$grilling` 빈틈 훑기** — 점검표에서 아직 안 닫힌 것 · 말 없이 가정한 것 · 앞 결정이 바뀌어 다시 열린 것만 1~2라운드 묻는다. 없으면 「빈틈 없음」 한 줄로 넘어간다.

## 문서 마무리 — 사용자 입력 없이
논의 중 적은 칸을 다듬고 빈 칸을 채운다: SOLUTION 0~5절 · ARCHITECTURE 0~6절(실행 형태는 과제설정 2·3절과 같게, 과제설정 3절 「예」인 인프라마다 담당 모듈과 검사 이름) · PLAN 2~5절(하드 제약 행마다 테스트 이름). 계약 파일의 값 이름(방향·필드·형식)은 계약 테스트 이름에 그대로. PLAN 2절 「가정」 행이 솔루션 DM 이 실무자에게 알릴 기본값 목록이다.

## 솔루션 브리핑 — 정한 것 정리
**앞 = 무엇을 왜**: 해법 한 문장 · 이유 · 실무자가 받는 것과 부분마다 푸는 문제 · 튀는 경우와 대처 · 안 할 것 · 실무자에게 알릴 기본값. **뒤 = 점검표 ①~⑫ 를 표로, 행 생략 없이** — 항목마다 「정함: 요지 · 적은 곳」 또는 「미처리: 이유」(줄여 쓰다 ⑫가 빠지면 사용자는 작업 계획 없이 넘어간다고 느낀다. 사용자는 미처리와 이상한 줄만 짚는다). 사용자가 「모듈 합쳐」「워커 하나 더」 식으로 고치면 반영해 다시 보인다. 서술형이 「왜 이렇게 나눴나」를 묻는다. 끝 `다음 입력(오케): 「OK」(또는 정정)`.

## 「OK」 — 솔루션 DM 안내 · 스캐폴드와 브리프를 먼저
1. **중간 응답으로 먼저** DM 안내: `새 탭 → codex → /permissions Full Access → /model → 「harness/roles/DM.md 읽고 솔루션 DM 시작해」 → 탭 이름 DM`(M1 DM 탭을 그대로 쓰려면 그 탭에 같은 문장). 마지막 줄 `다음 입력(DM): harness/roles/DM.md 읽고 솔루션 DM 시작해`. 턴은 끝내지 않는다.
2. 같은 턴에 **스캐폴드 서브에이전트**. 프롬프트 = `docs/ARCHITECTURE.md` 경로 + 폴더 규약(`src/<모듈>/` · `tests/<모듈>/` · `tests/contract/` · `tests/e2e/`) + 「시그니처만 있는 빈 파일 · 모듈당 계약 테스트 1개 이상(PLAN 2절 이름 그대로) · SOLUTION 4절의 경계값 테스트 이름만 · 구현 금지」. 화면이 있으면(점검표 ⑦) 같은 서브가 `bash harness/starter/shadcn/make.sh src/ui` 도 돌린다(10분 넘으면 멈추고 보고 — `harness/guides/DESIGN.md`).
3. **기다리는 동안** `docs/brief/<역할>.md` 를 역할마다 쓴다 — 꼴은 `$handoff` 「브리프」 5필드(정본) + `harness/guides/STAGES/M3.md` 「역할」의 자기 절 포인터. 워커 수·역할은 점검표 ⑫ 그대로(코어 · 통합 · 화면 + 필요하면 서비스).
4. 스캐폴드가 끝나면(`wait_agent` 긴 timeout) 계약 테스트를 **실행해 빨강인 것을 확인**(`harness/verify.sh "<명령>"` → FAIL 이 정상) · 스캐폴드 + 브리프 커밋 → 턴을 끝내고 DM queue 를 기다린다.

미리 하는 이유: 실무자 반응은 작은 보정(화면 항목 · 흐름 순서 · 기본값)이라 모듈 경계를 거의 바꾸지 않는다. 확정 뒤엔 바로 워커를 켠다.

## 솔루션 DM 이 도는 동안 (오케)
- `[DM→오케] 솔루션 변경: …` 은 그때그때 SOLUTION·ARCHITECTURE·PLAN 에 반영하고 `$decision`. 모듈 경계·계약(ARCH 2·3절)이 바뀌면 스캐폴드·계약 테스트·해당 브리프도 **변경점만** 고쳐 커밋한다. 실무자 반응은 작은 보정의 재료다 — 해법을 다시 탐색하거나 실험을 다시 돌리지 않는다.
- `[DM→오케] 가능한가: …` 은 한 줄로 답한다.
- `[DM→오케] 치명: …`(합의한 문제를 이 솔루션이 못 푼다 · 하드 제약을 어긴다)이면 사용자에게 알리고 점검표의 해당 항목으로 돌아가 같이 정한다. 그때만 스캐폴드·브리프를 다시 만든다.

## 「솔루션 확정」
DM 이 종료 브리핑을 하고 사용자가 「확정」을 치면 `[DM→오케] 솔루션 확정` 을 queue 한다(사용자가 직접 쳐도 같다). 실무자 반응은 DM 이, 설계는 오케가 끝냈다 — 다시 확인하지 않는다. 받으면:
1. `solution` 태그 커밋 · PLAN 1절 실제 시각.
2. **탭 안내 한 번에** — 「탭 N개를 켜 주세요」 + 탭마다 한 줄(문장은 `harness/guides/편성.md` 「새 탭 안내」). 끝 `다음 입력(사용자): 탭을 켜고 붙이기 — 그 뒤 칠 것 없음`.
3. 워커는 브리프 파일을 읽고 **바로 시작**한다. `[<역할>→오케] 준비됨 <UUID>` 는 등록 확인이다 — 세션.txt 와 대조만 하고 답하지 않는다. 역할별 할 일은 브리프와 `M3.md`.
4. 모든 워커의 「준비됨」이 오면 `M3 시작` — `docs/HANDOFF.md` 를 지금 기준으로 쓰고 커밋한다(승계하지 않아도 쓴다 — 새 세션이 이어받을 의도 문서가 증거다). 검증 체계 결정은 `docs/DECISIONS.md` D0 에 있다. **여기가 승계 권장 지점**이다. → `M3.md`.
