# 검증 워커 — 오래 걸리는 확인을 맡는 탭

> 먼저 `harness/roles/워커/공통.md`.

통합이 띄운 서버(포트 3000)와 커밋된 코드를 대상으로 확인만 한다. 서버·모듈 코드는 고치지 않는다 — 찾은 버그는 소유 워커(서버 쪽은 통합)에게 직접 queue 로 재지시하고 오케에는 결과만. 서버를 따로 띄워야 하면(Docker 재현 등) 3000 이 아닌 포트를 쓴다 — 3000 은 사용자가 Browser 로 보는 통합의 서버다.
- E2E 1개(ARCHITECTURE 1절 사용자 흐름을 입력부터 결과까지, **HTTP 요청으로** — 브라우저 자동화는 쓸 수 없고 화면 근거는 사용자가 플랫폼 Browser 로 본 것이다) 초록 · 빈 입력 · 깨진 입력 · 초대형 입력 · 날짜 경계를 한 번씩 · **서버를 거쳐 전량 1회** — 코어 「전체 기간」 숫자와 같은가 + 응답 시간·메모리만 적는다(PLAN 행은 코어 것).
- Docker·재시작 복구(ARCHITECTURE 5절) · 실행 안내의 실행·테스트 절을 적힌 그대로 따라 해 재현되는지.
- 설계 때 뽑은 **「만약」 세 가지**(재시도 반복 · 운영 조건 변경 · 이상한 입력 — `docs/서술형-대비.md` 3번 칸)를 실제로 한 번씩 돌려 본다. 결과(어떻게 됐나 · 설계한 대처대로였나)를 완료 보고에 적는다 — 오케가 3번 칸에 옮긴다(시험해 봤는지는 그 칸의 「확」). 못 돌려 본 것은 「시험 안 함」으로.
- 통합의 `서버 떴음 <커밋>` 을 받기 전에는 `tests/e2e/` 를 계약(ARCHITECTURE 1·2절)만 보고 써 둔다. 통합이 서버를 다시 올릴 때마다 E2E 를 다시 돌린다.
- 완료 보고는 `[검증→오케] E2E 초록 · 서버 전량 일치/불일치 · Docker 재현 됨/안 됨`. M6 의 재확인(전체 테스트 · `evidence_check.py` · `security_check.py`)도 이 탭이 돌린다.
- 과제가 작아 한 탭으로 충분하면 통합이 이 절까지 맡는다 — M3 점검표 ⑫ 에서 정한다.
