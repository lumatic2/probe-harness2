# 대기행렬·리틀의 법칙·운영 곡선 (Queueing, Little's Law, Operating Curve)
> WIP = 처리율 × 사이클타임이고, 가동률이 용량에 다가가면 사이클타임이 비선형으로 폭증한다는 것을 Kingman 근사로 그린다. 붙는 과제 유형: ② ⑥, 설명 전반. 코드: `../code/queueing_operating_curve.py`

## 바로 쓰는 칸
- **쓸 점**: 가동률이 용량에 다가가면 사이클타임이 비선형으로 폭증하는 운영 곡선과 공장 CT·WIP 를 근사식으로 낸다.
- **필요한 컬럼**: `stations`(station, m, te, visits, ca2, cs2)와 투입률 `lam`. 장비군 대수·공정시간·방문 횟수가 없으면 못 쓴다.
- **한 줄 실행**: `python code/queueing_operating_curve.py` (methods 폴더에서) — 합성 장비군 3개에서 투입률별 공장 CT·WIP·병목 가동률을 출력. 내 데이터로 쓸 때 부를 함수: `network`, `curve`, `simulate_gg1`
- **출력**: 장비군별 가동률·대기·사이클타임 표, 공장 CT·WIP, 가동률 vs 사이클타임 곡선(X-factor).
- **하지 말 것**: 공시 가동률(인원·수율 기준)을 곡선의 u 에 넣지 않는다 — 장비 단위 값을. 곡선은 정상상태 평균이라 과도기엔 시뮬레이션.
- **대신 쓸 수 있었던 것 / 안 쓴 이유**: 디스패칭 규칙 시뮬레이션 · 몬테카를로 — 가동률과 평균 대기·사이클타임의 관계로 가동률 상한과 목표 WIP 를 정하려면 이 기법을 고르고, 램프업·고장 직후의 과도기나 규칙별 효과, LOT 개별 일정이 필요하면 시뮬레이션을, 입력이 흔들릴 때 결과의 범위가 필요하면 몬테카를로를 쓰며 곡선은 정상상태 평균만 준다.

## 이럴 때 꺼낸다
- 과제 문구 신호: "대기시간", "사이클타임·TAT", "WIP 상한", "병목 가동률", "가동률을 높이면 좋은가", "목표 WIP 를 정하라".
- 데이터 모양 신호: 장비군별 장비 수·평균 공정시간, LOT 투입률, 공정 변동(분산) 또는 과거 공정시간 샘플.
- 꺼내지 말아야 할 때: 규칙별 우선순위 효과를 보려면(→ 디스패칭 규칙 시뮬레이션). 개별 LOT 의 정확한 일정이 필요하면(→ 제약 프로그래밍 일정). 곡선은 평균 거동만 준다.

## 입력 → 출력
입력 (DataFrame)

| 표 | 컬럼 | 의미 | 단위 |
|---|---|---|---|
| `stations` | `station` | 장비군 이름 | 문자열 |
| | `m` | 병렬 장비 수 | 대 |
| | `te` | 평균 공정시간 | 시간 |
| | `visits` | LOT 1개당 그 군 방문 횟수(재진입) | 회 |

출력: 장비군별 가동률·대기·사이클타임 표, 공장 CT·WIP, 운영 곡선 표 `utilization, cycle_time, x_factor`(CSV 로도 저장), "X배 지점 가동률" 목록. 합성 예: 단일 장비 가동률 80% → CT 5배, 90% → 10배, 95% → 20배.

## 핵심 개념
- 리틀의 법칙: `WIP = λ × CT` (λ = 처리율). 처리율이 같으면 WIP 를 줄이는 것과 CT 를 줄이는 것은 같은 일.
- Kingman (G/G/1): `Wq ≈ (ca² + cs²)/2 × u/(1-u) × te`. 다중 장비(m 대)는 Erlang C 에 같은 변동 보정(Allen-Cunneen). `CT = Wq + te`, X-factor = CT/te.
- `u/(1-u)` 때문에 u = 90% 에서 대기는 u = 50% 의 9배, u = 95% 에서 19배다 (M/M/1, `Wq/te`).

## 반도체 현장에서
- SLIM 은 단계별 목표 사이클타임·목표 WIP 계산에서 출발해 DRAM 사이클타임을 80일+에서 30일 미만으로 줄였다 (S2; 이해관계 있는 저자·반사실 가정 주의).
- Intel 램프업 연구는 운영 곡선 위에서 "용량 여유를 포기하지 말라"고 권했다: 여유 ±5% 안의 편차에는 둔감하나 그 밖에서는 빠르게 나빠진다 (S12, 수치 예제 기반).
- 병목 가동률 상한과 목표 WIP 를 정하는 근거 그림으로 쓴다.

## 화면 한 장
- 가동률(x, 50~99%) vs 사이클타임/X-factor(y) 곡선. 현재 위치 점과 "여유 5%" 구간을 색 띠로 표시하고, 슬라이더를 움직이면 점이 곡선 위를 이동하며 WIP·CT 숫자가 바뀐다. 변동계수 ca²/cs² 를 줄이면 곡선이 아래로 내려가는 것도 같은 화면에.

## 함정
- 공시 가동률은 장비 OEE 가 아니다 — 인원·수율 기준이다 (SK하이닉스 사업보고서 표 각주 「가동인원 및 수율을 고려하여 계산」). 곡선의 u 에는 장비 단위 값을 넣는다.
- `ca²=cs²=1`(지수) 가정이 현장에서 틀리면 곡선이 어긋난다. 변동이 큰 장비일수록 위로 올라간다.
- 재진입은 `visits` 로 센다. 같은 장비군을 두 번 지나는 LOT 은 그 군의 부하를 두 배로 만든다.
- 곡선은 정상상태 평균이다. 램프업·고장 직후 같은 과도기에는 시뮬레이션(디스패칭 규칙 시뮬레이션)을 쓴다.

## 한 문장 설명 · 예상 질문
- 한 문장: "가동률 95%를 노리면 사이클타임이 이만큼 늘어납니다 — 여유 5%의 값이 이 곡선입니다."
- Q. 근사식이 얼마나 정확한가? → 포아송 도착이면 정확하고, 아니면 합성 검증에서 7% 안팎 오차였다. 현업 데이터에서는 `ca²`·`cs²` 를 실측해 넣는다.
- Q. 가동률이 높을수록 좋은 것 아닌가? → 사이클타임·WIP 와 맞바꾸는 곡선을 먼저 보이고, 선택은 현업이 한다 (Intel 램프업 논문의 권고가 「관리자가 받아들이기 어렵지만 용량 여유를 포기하지 말라」였다, S12).

## 부록 — 검증 기록과 근거

### 검증 (하드체크)
- 코드 끝 assert:
  - ① M/M/1 에서 근사식 = 폐쇄형 `W = 1/(μ-λ)` (오차 1e-12).
  - ② 다중 장비 대기가 Erlang C 를 쓰지 않고 출생-사망 정상분포의 수치합(대기열 길이 → 리틀)으로 다시 계산한 값과 일치.
  - ③ Lindley 재귀 시뮬레이션 30만 건과 비교: M/M/1 오차 1.0%, M/G/1(cs²=0.25) 0.1% (포아송 도착이면 정확), 비포아송(ca²=cs²=0.5) 7.2% — 근사임을 수치로 보인다.
  - ④ 시뮬레이션에서 도착/퇴장 사건 스윕으로 구한 평균 재고 = λ × W (리틀).
  - ⑤ 곡선이 증가·볼록.
- 현장에서 추가할 경계값 테스트 2개: u → 0 에서 CT → te, u ≥ 1 에서 `network()` 가 과부하 에러를 내는지.

### 손익 환산
- 공식: 리틀 → WIP 현금 = 하루 원가 흐름 × ΔCT × 반영률 (리틀의 법칙). 처리량 쪽은 병목 산출 +0.1% = 연 2,136억원 (처리량 회계, 2Q26 연환산·DRAM 전체가 병목이라는 상한 가정, 추정).
- 예시(추정): 병목 가동률 상한을 95% → 90% 로 낮추면 M/M/1 기준 CT 가 절반(20배 → 10배)이 되지만 병목 산출은 약 5.3% 줄어 상한 약 11.2조원/년(2,136억 × 52.6)의 처리량을 포기한다. 곡선은 "CT 를 얻는 값이 처리량"임을 보이는 도구일 뿐 어느 점이 옳은지는 현업이 고른다 — 이 식은 상한이며 실제 병목 비중을 곱해 줄인다.
