# 강건·시나리오 계획 (Robust & Scenario Planning)
> 여러 시나리오(공정시간 변동·장비 고장) 전체에서 나쁘지 않은 배정 — 평균 최적, 최악 경우 최적, 후회 최소 해를 풀어 새 시나리오에서의 p90 지연을 비교한다. 붙는 과제 유형: ② ⑥. 코드: `../code/robust_scenario.py`

## 바로 쓰는 칸
- **쓸 점**: 여러 시나리오에서 나쁘지 않은 배정(평균 최적·최악 최적·후회 최소)을 풀어 새 시나리오의 p90 지연을 비교한다.
- **필요한 컬럼**: `jobs`(job, minutes, due)와 시나리오 `P[s,j]`·`D[s,m]`. 고장 이력·공정시간 분산이 없어 시나리오를 못 만들면 못 쓴다.
- **한 줄 실행**: `python code/robust_scenario.py` (methods 폴더에서) — 합성 시나리오로 4개 계획을 새 시나리오에서 비교. (ortools 필요) 내 데이터로 쓸 때 부를 함수: `make_scenarios`, `solve`, `evaluate`
- **출력**: 4개 계획의 새 시나리오 평균·p90·최악 총 지연과 배정 문자열, 지연 히스토그램.
- **하지 말 것**: 계획에 쓴 시나리오로 평가하지 않는다(새 시나리오로). 세 해가 같으면 같다는 것이 결론이다 — 차이를 억지로 만들지 않는다.
- **대신 쓸 수 있었던 것 / 안 쓴 이유**: 몬테카를로 · 최소 변경 재스케줄 — 한 번 정하면 되돌리기 어려운 배정을 교란 전에 골라야 하면 이 기법을 고르고, 이미 정한 일정의 결과 범위만 보면 되면 몬테카를로를, 교란이 난 뒤의 복구라면 최소 변경 재스케줄을 쓰며 실시간 재스케줄이 가능하면 사전에 시나리오를 묶을 이유가 작다.

## 이럴 때 꺼낸다
- 과제 문구: "장비 고장에도 무너지지 않는", "변동", "최악의 경우", "긴급 LOT 이 끼어들어도", "불확실성", "안정적인 일정".
- 데이터 모양: LOT 처리시간·납기 + 불확실성 정보(고장 이력에서 뽑은 다운 확률·길이, 공정시간 분산) / 시나리오 표(행=시나리오).
- 꺼내지 말아야 할 때: 불확실성 분포를 전혀 모를 때(시나리오를 지어내게 된다 → 먼저 민감도 분석 민감도로 중요한 가정부터), 한 번 정하면 되돌릴 수 없는 결정이 없을 때(실시간 재스케줄이 가능하면 디스패칭 규칙 시뮬레이션 디스패칭).

## 입력 → 출력
| 입력 | 의미 | 단위 |
|---|---|---|
| `jobs` DataFrame | `job` LOT 이름 · `minutes` 공칭 처리시간 · `due` 납기(교대 시작 후) | 분 |
| `P[s,j]` | 시나리오 s 에서 LOT j 의 처리시간 (`make_scenarios`로 생성) | 분 |
| `D[s,m]` | 시나리오 s 에서 장비 m 의 시작 지연(다운) | 분 |
- 출력: 4개 계획(공칭·평균 최적·최악 최적·후회 최소)의 새 시나리오 2000개 평균·p90·최악 총 지연과 배정 문자열.
- → 실행 결과는 부록
- 현장에서 끼우기(`code/` 에서 `import robust_scenario`):
```python
P, D = make_scenarios(jobs, 40, seed=1)      # 현장에서는 고장 이력 분포로 교체
plan = solve(jobs, P, D, 'worst')                # 'mean' | 'worst' | 'regret'(ref=시나리오별 최적)
```

## 핵심 개념 (5줄 이내 + 수식 1~2개)
- 1단계 결정 x(장비 배정)를 시나리오 s=1..S 에 걸쳐 고정하고, 시나리오별 비용 `Tot_s(x)`(총 지연)로 평가한다.
- 평균 최적 `min Σ_s Tot_s`, 최악 최적 `min max_s Tot_s`, 후회 최소 `min max_s (Tot_s(x) − Tot_s*)` (Tot_s* = 시나리오 s 만 보고 푼 최적).
- 최악·후회 해는 나쁜 날의 꼬리를 줄이는 대신 평균을 조금 내줄 수 있다 — 단 새 시나리오에서는 평균 최적이 과적합으로 더 나쁠 수도 있다. 반드시 계획에 안 쓴 시나리오로 평가한다.
- 장비 안 순서는 납기순(EDD)으로 고정하고 완료시각은 시나리오 실현값이 정한다.

## 반도체 현장에서 (용도 2~3줄, 사례 수치는 출처와 함께)
- 장비 다운·긴급 LOT 투입에도 무너지지 않는 배정. 확인된 가장 가까운 사례는 ECCO 의 2026 Edelman 결선작(대규모 확률 MIP 로 536개 매장 보충 주문, 핵심 운영비 1.09% 절감, S20 자사 신고) — 반도체 특화 강건·확률 계획 운영 사례는 확인하지 못했다(외부 출처 미확인).
- 아래 수치는 모두 합성 시나리오의 코드 출력이다.

## 솔버/코드가 하는 것 · AI 가 하는 것
- 결정론: CP-SAT 정수 모형(배정 변수 + 같은 장비 쌍 변수), 세 가지 목적 각각 최적해, 새 시나리오 평가.
- AI: 질문 → 시나리오 파라미터. 예 1) "장비가 자주 고장 나면?" → `{down_prob: 0.4}`. 예 2) "긴급 LOT 이 한 개 끼어들면?" → `{add_job: {minutes: 120, due: 300}}`. 시나리오 재생성 후 솔버 재실행.
- 설명 틀: "평균만 보면 ○ 배정이 좋지만 열 번 중 아홉 번 지연이 ○분 이내라는 기준(p90)으로는 ○ 배정이 ○% 낫습니다. 대신 평균 지연이 ○분 변합니다."

## 화면 한 장
- 그룹 막대: x=계획(공칭·평균 최적·최악 최적·후회 최소), 막대 3개=평균/p90/최악 총 지연. p90 막대 강조. 옆에 새 시나리오 지연 히스토그램 겹쳐 그리기.

## 함정
- 시나리오가 적으면 평균 최적이 과적합하고 최악 해도 계획 시나리오의 최악에만 맞는다. 평가는 반드시 새 시나리오로.
- 데이터에 따라 세 해가 같아질 수 있다(여유가 크면 하나의 배정이 모두에서 최적). 같다는 것 자체가 결론이다 — 억지로 차이를 만들지 않는다.
- 최악 해는 극단 시나리오 하나에 끌려간다. 시나리오 생성기의 꼬리를 점검한다. 후회 최소는 시나리오별 최적을 먼저 풀어야 해서 느리다.
- 이 코드는 다운을 "장비 시작 지연"으로 단순화했다. 중간 고장은 모형을 바꿔야 한다.

## 한 문장 설명 · 예상 질문
- "가장 좋은 날이 아니라 나쁜 날에도 지키는 일정입니다 — 계획에 안 쓴 시나리오 2000개에서 p90 지연이 10% 낮습니다(합성 데이터)."
- Q. 시나리오는 어디서 나왔나? → A. 합성이다. 현장에서는 고장 이력의 다운 확률·길이, 공정시간 분산에서 뽑으며 시나리오 수와 분포는 화면에 같이 적는다.
- Q. 평균 최적이 더 나쁘게 나온 이유는? → A. 시나리오 40개에 맞춘 과적합이다. 그래서 계획용과 평가용 시나리오를 분리했다. 시나리오 수를 늘리면 차이가 줄 수 있다.

### 검증 (하드체크)
- 코드 끝 assert 가 독립 재검사: ① 3⁹=19,683개 배정을 전수 평가(솔버와 다른 코드)해 평균 최소 17,373·최악 최소 995·최대 후회 최소 315 가 CP-SAT 해의 값과 일치 ② 후회는 모든 해에서 0 이상 ③ 최악 해의 최악값 ≤ 평균 해의 최악값, 평균 해의 합 ≤ 최악 해의 합.
- 현장 추가 경계 테스트: (a) 모든 시나리오를 공칭과 같게(`P`=공칭, `D=0`) 만들면 세 해의 시나리오별 총 지연이 같은지(실측: 세 해 모두 187분) (b) 시나리오를 1개만 주면 평균·최악·후회 해가 모두 그 시나리오의 최적과 같은지.
