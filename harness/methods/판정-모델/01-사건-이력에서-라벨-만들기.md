# 사건 이력에서 라벨 만들기 (예측 시점 · 관측 창 · 예측 구간)
> 접근법 선반: [알람 관리](../../approaches/공학/인간공학/01-알람-관리.md)(알람 연쇄를 사건으로 묶는 관점) · [설비](../../approaches/반도체-현장/흐름-설비-계획/02-설비.md)(정지·가동 이력을 읽는 틀)

> 알람·정지 이력에는 라벨 열이 없다. 「언제 판정하나(t₀) · 얼마 전까지 보나(W) · 얼마 앞을 맞히나(H)」를 먼저 정해 표본과 0/1 라벨을 코드로 만들고, t₀ 뒤의 정보가 특징에 새지 않았는지 검사한다. 붙는 과제 유형: ① ② (이상·정지 예측, Q-Time 위험). 코드: `../code/event_label_builder.py`

## 바로 쓰는 칸
- **쓸 점**: 라벨 열이 없는 알람·정지 이력에서 판정 시점·관측 창·예측 구간을 정해 표본과 0/1 라벨을 만들고 미래 정보가 특징에 새지 않았는지 검사한다.
- **필요한 컬럼**: `events`(`eqp_id, ts, code, severity`)와 `outcomes`(`eqp_id, ts, end_ts, type`) — 사건 시각이 없으면 t₀ 를 못 정해 못 쓴다.
- **한 줄 실행**: `python code/event_label_builder.py` (methods 폴더에서) — 합성 6대 이력으로 H 별 양성 비율 (scikit-learn 필요). 내 데이터로 쓸 때 부를 함수: `build_samples`, `audit_features`
- **출력**: `samples` 표(t₀·특징·`label`·제외 사유 진행 중/검열)와 H=4·8·24h 별 양성 비율·표본 수·제외 건수 표.
- **하지 말 것**: 진행 중 표본과 데이터 끝(검열) 표본을 라벨 0 으로 두지 않는다 — 거짓 음성이 되니 제외한다.
- **대신 쓸 수 있었던 것 / 안 쓴 이유**: [누수 없이 나누기](02-누수-없이-나누기.md) 부터(이미 행마다 결과 열이 있는 표) · [장비 상태 이력 가용도](../이벤트-로그-분석/03-장비-상태-이력-가용도.md)(지난 정지를 세기만 할 때) — 알람·정지 이력에서 앞으로의 사건을 미리 맞히는 질문일 때만 라벨을 직접 만들고, 결과 열이 이미 있거나 지난 사건을 집계하면 되면 대안으로 충분해 안 쓴다.

## 이럴 때 꺼낸다
- 과제 문구: "어떤 알람이 정지·스크랩으로 이어지나", "Q-Time 위반 위험 로트를 미리", "고장 전에 알려 달라", "예측 모델".
- 데이터 모양: 사건 로그(시각·장비·코드)만 있고 라벨 열이 없다 / 정지·스크랩 이력이 알람 이력과 따로 있다.
- 꺼내지 말아야 할 때: 이미 행마다 「불량 여부」 열이 있는 표(→ 02 분할부터). 사건의 시각을 하나도 모를 때(시각이 없으면 t₀ 를 못 정한다).

## 입력 → 출력
| 입력 | 컬럼 | 의미 |
|---|---|---|
| `events` | `eqp_id, ts, code, severity` | 알람 이력(ts = 시간 단위 실수) |
| `outcomes` | `eqp_id, ts, end_ts, type` | 정지(DOWN)·스크랩 이력. `ts` = 사건 시작, `end_ts` = 끝 |
| `t0_table` | `eqp_id, t0` | `grid_t0`(장비×고정 간격) 또는 `episode_t0`(알람 연쇄의 시작) |
| 인자 | `W, H, data_end` | 관측 창 · 예측 구간 · 데이터 끝 시각 |
- Q-Time 이면: `lot_moves(lot_id, step, track_out_ts, next_track_in_ts, qtime_limit)` → `t0 = track_out_ts`, 라벨 = `next_track_in_ts − track_out_ts > qtime_limit`. 이 변환은 이 코드가 풀어 주지 않는다 — 사건 표 모양으로 바꿔 `outcomes` 에 넣거나 직접 한 줄로 만든다(**결정 필요**: 결측 `next_track_in_ts`(아직 대기 중)를 검열로 볼지는 현업이 정한다).
- 출력 `samples`: `eqp_id, t0, n_alarm_W, max_sev_W, hours_since_last_alarm, feat_max_ts, label, excluded_reason(in_progress|censored|"")` + `audit_features` 가 돌려주는 「허용 목록 밖 컬럼」.
- 실행: `python code/event_label_builder.py` (numpy·pandas, 하드체크의 AUC 만 scikit-learn, 약 3초). 현장에서 바꿔 끼우는 곳: `events`·`outcomes` DataFrame, `W`·`H`, `LEGIT_FEATURES`(t₀ 에 알려진 컬럼 허용 목록).
- → 실행 결과는 부록

## 핵심 개념
- **t₀**(판정 시점) · **W**(관측 창 `(t₀−W, t₀]`) · **H**(예측 구간 `(t₀, t₀+H]`). 라벨 = `1[(t₀, t₀+H] 안에 사건 시작이 1건 이상]`. 특징은 W 안에서 t₀ 에 이미 알려진 것만.
- 표본에서 뺄 것: **진행 중**(t₀ 에 이미 정지 상태 → 「정지를 예측」하는 표본이 아니다), **검열**(데이터 끝에서 H 보다 가까운 t₀ → 라벨 미확정, 0 으로 두면 거짓 음성).
- 알람 연쇄는 사건 하나로 묶는다. 묶기 규칙을 「직전 알람이 quiet 시간 넘게 이전이면 새 사건 시작」으로 두면 t₀ 에서 과거만 봐도 되므로 미래를 쓰지 않는다(추론: 원천의 사건 묶기 권고를 인과적 규칙으로 옮김).
- H 는 현장 행동 시간에 맞춘다. 한 산업 사례 논문은 예측 구간의 크기가 결과를 좌우한다고 결론짓는다(근거 참조). 작은 H 2~3개를 표로 보인다.

## 반도체 현장에서
- **알람 → 정지·스크랩**: t₀ = 알람(사건) 발생 시각, W = 직전 24시간 같은 장비의 알람·FDC 요약, H = 다음 4·8·24시간 안 `EQP_DOWN` 또는 해당 장비 경유 로트 스크랩. 라벨 단위는 「묶은 알람 사건」(추론).
- **Q-Time 위반 위험**: t₀ = 로트가 스텝 A 를 끝내 큐에 들어간 순간, 라벨 = (스텝 B 착공 − A 완료) > `qtime_limit`. 특징은 t₀ 의 큐 길이·다음 스텝 가용 장비 수·우선순위·남은 여유·시간대(추론). **Q-Time 위반을 기계학습으로 예측한 공개 사례는 이번 조사에서 찾지 않았다(`미확인`)** — 이 정의는 원천이 사례 논문의 정의를 옮긴 추론이다.
- 가장 흔한 누수는 실제 대기 시간·B 착공 시각을 특징에 넣는 것, t₀ 뒤에 일어난 장비 다운을 「현재 가용 장비 수」에 섞는 것이다(추론). 알람 연쇄를 가진 이벤트 로그 쪽 계산은 [이벤트 로그 분석](../이벤트-로그-분석/README.md) 모듈과 짝이다.

## 솔버/코드가 하는 것 · AI 가 하는 것
- 결정론: 창 자르기, 라벨, 진행 중·검열 제외, 사건 묶기, 허용 목록 검사. 시각 비교를 전부 코드가 한다.
- AI: 표본 단위·H 후보를 사용자에게 묻는 문장, 각 컬럼이 t₀ 에 알려지는지 「의심 목록」 초안(최종 판정은 사람). 예) "정지 사유 코드는 정지가 끝나야 채워집니까?" → 채워지면 금지 컬럼.
- 설명 틀: "표본은 ○(장비×시각)이고, 각 시점에서 직전 ○시간의 알람으로 다음 ○시간 안 정지를 맞힙니다. 양성 비율은 ○%, 진행 중 ○건·끝단 ○건은 뺐습니다. t₀ 뒤에야 아는 컬럼 ○개는 쓰지 않았습니다."

## 화면 한 장
- 장비 1대의 타임라인: 알람 점, 정지 막대, t₀ 마다 W(회색)·H(주황) 띠와 라벨 0/1. 옆에 「H = 4/8/24h 별 양성 비율·표본 수·제외 건수」 표.

## 함정
- 사건이 이미 진행 중인 표본과 데이터 끝 표본을 라벨 0 으로 두는 것. 거짓 음성이 되어 양성 비율이 낮아 보인다.
- 알람 연쇄를 묶지 않아 한 정지 사건이 수십 개 양성 표본이 되고 같은 사건이 학습·시험 양쪽에 들어간다(02 의 중복 누수).
- 관측 창을 늘리면 좋아질 것이라는 믿음 — 사례 논문은 과거 데이터를 늘린다고 꼭 좋아지지 않는다고 적는다.
- `data_end` 근처 H 구간의 사건이 아직 기록되지 않았을 수 있다(기록 지연). 데이터 끝 여유를 H 보다 더 둔다(추론).

## 한 문장 설명 · 예상 질문
- "모델보다 먼저 '언제, 무엇을 알고, 얼마 앞을 맞히나'를 정했습니다."
- Q. 왜 H 를 여러 개 보이나? A. 예측 구간이 길수록 양성이 늘어 쉬워지고 짧을수록 어렵습니다. 현장이 조치할 수 있는 시간에 맞춘 H 의 점수만 의미가 있습니다.
- Q. 정확도가 높게 나온 이유가 누수 아닌가? A. 특징의 가장 늦은 시각이 t₀ 이하인지 행마다 검사하고, 미래 컬럼을 일부러 넣으면 검사가 잡는 것을 보여 드립니다.

## 부록 — 검증 기록과 근거

### 검증 (하드체크)
- 코드 끝 assert:
  - ① 손으로 만든 소형 이력(2대·20행)의 라벨·제외 사유·특징이 손정답과 정확히 일치(위쪽 끝 포함·아래쪽 끝 제외 경계 포함)
  - ② 합성 이력에서 특징에 쓴 가장 늦은 시각 ≤ t₀ 를 전수 확인
  - ③ 순수 파이썬 루프 구현과 400행 대조
  - ④ t₀ 이후 알람의 심각도를 99 로 바꿔도 특징이 같음
  - ⑤ H→0 이면 양성 0, H 를 키우면 양성 비율 증가
  - ⑥ 미래 정보 컬럼(다음 정지까지 남은 시간)을 넣으면 단일 AUC 가 허용 특징(0.755)을 크게 넘어(1.000) 검사가 작동하고 `audit_features` 가 그 컬럼을 잡음.
- 현장 추가 경계 테스트: (a) 사건 시작 시각이 정확히 t₀ 인 표본이 진행 중으로 빠지는지 (b) 같은 알람 연쇄가 학습·시험 양쪽에 들어가지 않는지(→ 02) (c) 데이터 끝 H 구간 표본이 0 이 아니라 제외인지.

### 합성 데이터 실행 결과
- 합성 결과(6대 60일, W=12h): H=1h 양성 0.96% · 4h 3.01% · 8h 5.85% · 24h 16.70% — H 가 양성 비율을 바꾸므로 H 마다 지표가 다르다. 알람 667건 → quiet 4h 로 묶으면 사건 382건.

### 손익 환산
- 이 단계는 비용을 줄이는 기능이 아니라 이후 모든 숫자의 정의다. 원천에 환산 수치가 없다. 경보를 받고 조치할 시간(H 의 하한)이 있어야 맞혀도 쓸모가 있으므로, H 가 현장 조치 시간보다 짧으면 그 모델의 가치는 0 으로 둔다(추론).
- 비용 숫자는 04 의 임계값 칸에서 가정 슬라이더로 둔다.
