# SLO와 오류 예산 (구글 SRE)

> [신뢰성공학](README.md) › 01 · 짝 기법: [민감도 분석](../../../methods/의사결정분석/02-민감도와-가정-바꿔-보기.md)
> 원 분야 사실에는 근거 등급을 달았고, 반도체로 옮긴 부분은 별도 표시가 없으면 **추론**이다. 모듈 주의는 [모듈 README](README.md), 표기는 [입구](../../README.md) 「표기」.

## 바로 쓰는 칸
- **쓸 점**: 가동률 100% 와 개별 협상 대신 분기 「오류 예산」 한 숫자로 개선 실험·변경 허락 여부를 정한다.
- **필요한 데이터**: eqp_state.csv(eqp_id, state, start, end), change.csv(ts, eqp_id, kind), slo.csv(eqp_group, metric, target). 목표(target)가 없으면 못 쓴다.
- **6시간 최소 형태**: 오류 예산 = (1−목표)×분기 시간, 소진 = 계획 외 정지 시간 / 예산. 화면: 장비군별 예산 게이지 + 남은 예산으로 가능한 실험 목록.
- **반문 하나**: 「팹은 가동률 100% 가 목표인데 실패 허용은 말이 안 된다」 → 구글도 100% 는 목표가 아니라 하고, 이미 빠지는 PM·평가 시간을 예산으로 관리하자는 것.
- **하지 말 것**: 구글의 99.999%·100배 비용 같은 수치를 팹 효과로 말하지 않는다. 생산 쪽에 멈춤 권한이 있어야 작동한다는 원문 단서를 빼지 않는다.

## 상세

**한 줄**: 「데이터센터 운영(구글 SRE)에서는 「안정성 100%」와 「빠른 변경」이 부딪칠 때 SLO(서비스 수준 목표)와 오류 예산을 쓴다. 핵심 논리는 100% 는 목표가 아니고, 신뢰성은 한 단계 올릴 때마다 비용이 비선형으로 커지므로, 목표치를 정한 뒤 남는 「허용 실패량」을 예산으로 두고 예산이 남으면 변경을 허락하고 다 쓰면 변경을 멈춘다 — 두 팀이 같은 숫자로 협상하게 만든다는 것이다. 「서비스 가용성」을 장비 가용 시간·Q-Time 준수율·레시피 변경 후 수율 유지로, 「배포」를 엔지니어링 변경(레시피 튜닝·하드웨어 개조·평가 웨이퍼 투입)으로 바꿔 대입하면 생산(가동률)과 기술(개선 실험) 사이의 장비 시간 배분 문제에 적용된다. 지금 방식(가동률 최대화 + 개별 협상)과 비교해 「분기 오류 예산 소진율」과 「예산 안에서 허락된 개선 실험 수」로 개선을 보일 수 있다.」
- **과제 문구 신호**(추론): 「가동률을 높이면 좋은가」「개선 실험 시간 배분」「생산 vs 기술」「변경 후 수율」「분기 목표」
- **가정 변환**

| 원 분야 가정 | 반도체 현장 대응물 |
|---|---|
| 요청 성공률 | 장비 가용 시간 비율 / Q-Time 준수 LOT 비율 / 웨이퍼 성공 처리율 |
| 배포(변경) | 레시피 튜닝, 장비 개조, 평가 웨이퍼 투입, 신규 부품 시험 |
| 개발팀 vs SRE | 기술(소자·공정 개발) vs 생산(양산관리) — 회사 비유 "양산기술 = 연주자, 양산관리 = 지휘자" |
| ISP 배경 오류율 | 계측 노이즈, 자연 변동 |
| 분기 예산 | 분기 장비별 '실험 허용 시간·허용 수율 손실' |

- **원 분야 사실**(원문):
  - 극단적 신뢰성은 비용이 들고 기능 개발 속도를 깎으며, 사용자는 높은 신뢰성과 극단 신뢰성의 차이를 잘 못 느낀다. 신뢰성 한 단계 개선이 직전 단계보다 100배 비용일 수 있다.
  - 가용성 목표는 "최소이자 최대" — 너무 넘겨도 낭비다. 예: 분기 99.999% 성공 SLO 면 오류 예산은 0.001%, 0.0002% 를 실패하게 만든 문제는 분기 예산의 20% 를 쓴다(원문 대응 수치).
  - SLO 를 맞추는 한 배포 계속, 예산을 다 쓰면 배포를 잠시 멈추고 시험·복원력에 투자한다. **단서**: 이 결과는 "SRE 팀이 SLO 가 깨지면 실제로 출시를 멈출 권한이 있을 때"에만 성립한다고 원문이 적는다.
  - 네트워크·데이터센터 장애도 예산을 깎는다. 배치·파이프라인 같은 비서빙 시스템도 '성공 처리 단위 비율'로 같은 원리를 쓴다.
- **하이닉스 적용 예**(추론): (a) 장비별 오류 예산 대시보드: 분기 SLO 대비 이미 쓴 손실과 남은 예산 → 남은 예산 안에서 개선 실험 일정 추천(제약 프로그래밍 일정 스케줄과 연결). (b) Copy Exactly([Copy Exactly!](../../경영학/생산운영관리/04-Copy-Exactly.md))의 '통제된 변경'을 숫자로: 변경 허용 = 예산 남음.
- **기준선과 지표**: 기준 = 가동률 목표 + 개별 협상. 지표 = 예산 소진율, 예산 초과 장비 수, 예산 안에서 수행된 개선 실험 수와 그 수율 효과, 협상 회의 수(추론).
- **6시간 최소 형태**: 데이터 `eqp_state.csv(eqp_id, state, start, end)`(SEMI E10 상태), `change.csv(ts, eqp_id, kind, approved_by)`, `slo.csv(eqp_group, metric, target)`. 계산: 분기 누적 가용률 → 오류 예산 = (1−목표)×분기 시간 → 소진 = 계획 외 정지 시간 / 예산. 화면: 장비군별 예산 게이지(초록·노랑·빨강) + "남은 예산으로 가능한 실험" 목록 + 소진 추이(번다운).
- **반론과 답**:
  - "팹은 가동률 100% 가 목표인데 '실패 허용'은 말이 안 된다" → 이게 바로 "당연하게 여겨 온 방식에 던지는 질문"이다. 구글도 100% 가 목표가 아니라고 쓴다 — 실제로는 이미 PM·평가·개조로 장비 시간이 빠지고 있으니, 그걸 협상이 아니라 예산으로 관리하자는 것.
  - 다만 **원문 단서대로 생산 쪽에 멈춤 권한이 있어야** 작동하므로 거버넌스 질문이 따라온다. "Q-Time 위반은 스크랩이라 예산 개념이 안 맞는다" → 그런 지표는 SLO 를 아주 높게 두고 예산을 사실상 0 으로 두면 된다(지표별로 다르게).
