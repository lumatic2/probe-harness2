# 엔지니어 업무 관점 — 「이상이 나면 누가 무엇을 보고 어떻게 넘기나」

> [업무-유틸리티-사람](README.md) › 01 · 짝 기법: [질문을 파라미터로](../../../methods/최적화/05-질문을-파라미터로.md), [관리도와 오경보 주기](../../../methods/품질과-신뢰성-통계/01-관리도와-오경보-주기.md), [다기준 의사결정](../../../methods/의사결정분석/03-다기준-의사결정.md) (+[알람 관리](../../공학/인간공학/01-알람-관리.md) 알람 관리, [구조화 교대 인계](../../공학/인간공학/03-구조화-교대-인계.md) 교대 인계, [FMEA](../../공학/안전공학/02-FMEA와-HAZOP.md) FMEA, [핵심 결정 기법(CDM)](../../공학/인간공학/05-핵심-결정-기법.md) CDM)

## 바로 쓰는 칸
- **쓸 점**: 이상이 났을 때 「누가 무엇을 보고 어떻게 넘기나」 — 알람→데이터→조치→기록·인계 흐름 도구가 6시간에 가장 만들기 쉽다(추론).
- **필요한 데이터**: 조치 기록 `note_id, eqp_id, occurred_at, symptom_text, action_text, downtime_min` 또는 알람 로그 — 없으면 못 쓴다.
- **6시간 최소 형태**: 조치 기록 텍스트 → 증상 유사 검색 → 원인·조치 후보(근거 note 인용) / 증상 입력창 → 추천 조치 카드 3장.
- **반문 하나**: 「AI 가 찾은 후보가 실제 어떤 위험이냐는 우리가 판단한다」 → 최종 판단 버튼은 엔지니어에게 두고 피드백을 다음 추천에 반영한다(추론).
- **하지 말 것**: 합성 Inform Note 를 실데이터처럼 꾸미지 않는다 — 화면에 「합성」 표시, 컬럼 예는 필자 설계라 `unique()` 로 확인한다.

## 핵심
- **이 눈이 던지는 질문**: 이상이 났을 때 누가 무엇을 보고 어떻게 넘기나?
- **과제 문구 신호**(추론): 「조치 기록」「Inform Note」「알람→사건」「인계」「변경 관리」「데이터 뽑기」「같은 불량에 대응이 제각각」「장비 이력 요약」「로그를 스펙과 대조」
- **핵심 지표와 공식**(원문 표는 부록)

| 지표 | 뜻 | 근거 |
|---|---|---|
| 조치까지 걸린 시간 | (추론) 이상 발생에서 조치 완료까지 | 지표 이름만 있음(외부 출처 미확인) |
| 반복 이상 건수 | (추론) 같은 장비·같은 증상이 다시 난 건수 | 벤더 주장, E4 취급 |
| 알람→사건 압축률 ★ | (추론) 알람 줄 수 ÷ 묶은 사건 수 | ★ 통념 |
| 관리도 오경보율 | 3σ 단독이면 평균 약 371점마다 1번, WECO 를 더하면 약 92점마다 1번 | NIST 경유, 알람 피로는 ★ |
| 관리한계 ≠ 규격한계 | UCL/LCL 은 공정이 보이는 범위, USL/LSL 은 고객·설계 한계 — 다른 선·다른 색 | 필자 요약(외부 출처 미확인) |
| 가용도 4종 | 같은 이름 다른 정의 | INFICON 글(E3) → 설비 관점 |

- **결정 직무**: 공정·장비 엔지니어 전반(장비 엔지니어·공정 엔지니어·품질보증). 직무 서술 인용은 부록 「결정 직무」.
- **데이터**: 조치 기록(Inform Note)·알람 로그·변경 이력·인계 메모. 컬럼 예는 전부 필자 설계 — 실제 열 이름은 `unique()` 로 확인(부록 「데이터」).
- **6시간 최소 문제**(추론): ① 조치 기록 텍스트 → 증상 유사 검색 → 원인·조치 후보(근거 note 인용). ② 알람 로그 → 같은 장비·시간창 묶기 → 사건 큐 + 「교대 인계 요약」 초안. ③ 지표 사전 — 부서별 정의를 한 화면에 나란히.
- **현장 사람이 할 반문**: ① 양산관리 「그 숫자, 우리 정의로는 다르게 나오는데요?」 ② 품질 「영향 범위는요?」 ③ 「AI 가 찾은 후보가 실제 어떤 위험이냐는 우리가 판단한다」 ④ 「Inform Note 말고 다른 데이터도 붙나요?」(추론)
- **옆 챕터로**: [알람 관리](../../공학/인간공학/01-알람-관리.md)(알람→사건 묶기) · [구조화 교대 인계](../../공학/인간공학/03-구조화-교대-인계.md)(인계서 초안) · [지식 경계와 경계 객체](../../경영학/조직과-지식/01-지식-경계와-경계-객체.md)(같은 데이터 다른 해석)
  - [행동별 자율성 단계표](../../컴퓨터과학/자율성-설계/01-행동별-자율성-단계표.md)(AI 제시·사람 판단) · [권한 상속 RAG](../../컴퓨터과학/정보보안/02-권한-상속-RAG.md)(조치 기록 검색의 권한)

## 부록 — 상세·인용·근거
### 무엇을 보나
- **무엇을 보나**: 기술보다 **일의 흐름** — 알람을 받고 → 데이터를 뽑고 → 원인 가설을 세우고 → 조치하고 → 기록·인계하고 → 다른 부서를 설득한다. 6시간 안에 가장 만들기 쉬운 것이 이 관점의 도구다(추론). 일의 박자: 양산관리 TL 의 '지금 당장' 이슈 인용은 [흐름·생산 관점](../흐름-설비-계획/01-흐름-생산.md) 부록 「결정 직무」(뉴스룸 「양산관리」).
- **근거로 확인한 업무 장면**

| 장면 | 근거 |
|---|---|
| 데이터 추출이 업무의 출발점 — 신입은 데이터 뽑기부터, Python·SQL 요구 | 뉴스룸 「양산관리」 |
| 「어떤 케이스에 어떤 데이터를 활용할지 판단하는 것은 끝없는 숙제」 | 같은 기사, 이희윤 TL |
| 같은 데이터, 다른 해석 → 주 1회 이상 회의로 「데이터의 의미를 통일」 | 같은 기사, 한진성 TL |
| 장비 이상·처리 결과를 다음 작업자·부서에 넘기는 문서 Inform Note, 같은 불량에도 대응이 제각각 | GaiA Biz 에이전트 글(2025-10-31, E2 자사) |
| 공정 변경 관리가 품질보증의 정식 업무 | 뉴스룸 「품질보증」 |
| 레시피 단위 인증(recipe-level quals)은 장비가 멀쩡해도 생산이 못 쓰는 시간을 만든다 | INFICON 가용도 글([설비 관점](../흐름-설비-계획/02-설비.md)) |
| 설계 변경 통지(ECN)가 나오면 팹 안 WIP 가 많을수록 영향 웨이퍼가 많다(절감액 식은 [공급망·계획 관점](../흐름-설비-계획/03-공급망-계획.md) 부록) | INFICON CT 글([공급망·계획 관점](../흐름-설비-계획/03-공급망-계획.md)) |
| R2R 이 레시피 관리를 자동화해 사람 실수를 없앴다 | Bode 외 IFAC 2002([계측·제어 관점](../품질-계측-후공정/02-계측-제어.md)) |
| FDC 알람의 오경보·미탐 | Moyne & Iskandar([품질·수율 관점](../품질-계측-후공정/01-품질-수율.md)) |
| 교대 직후 반복 이상까지 탐지했다는 벤더 주장 | Gauss Labs 대표 인터뷰 기사(E3, 벤더 주장이라 E4 취급) |
| 「Data quality (veracity) has been recognized as big data “V” of most importance」, 「data still cannot be blindly trusted in analytical solutions」 | Moyne & Iskandar(E2, 저자 판매사 소속) |
| 「incorporating SME is usually required to realize robust and maintainable solutions」 — 현장 전문가 지식은 계속 필요 | Moyne & Iskandar(E2) |

  교대 인계서의 실제 양식·알람 처리 SLA·변경 관리 결재 단계는 공개 1차 근거를 찾지 못했다 ★ — 현업 질문으로 남긴다.

### 핵심 지표와 공식 — 원문
- **핵심 지표와 공식**

| 지표 | 뜻 | 근거 |
|---|---|---|
| 조치까지 걸린 시간 | (추론) 이상 발생에서 조치 완료까지. 조치 기록의 `occurred_at`·`downtime_min` 같은 열로 잴 수 있는지 먼저 본다 | 지표 이름만 있고 정의식은 없다(외부 출처 미확인). 열 이름은 예시(필자 설계) |
| 반복 이상 건수 | (추론) 같은 장비·같은 증상이 다시 난 건수 | 지표 이름만 있음(외부 출처 미확인). 교대 직후 반복 이상 탐지는 벤더(Gauss Labs 대표) 주장, E4 취급 |
| 알람→사건 압축률 ★ | (추론) 알람 줄 수 ÷ 묶은 사건 수. 데모 문구 예: 「알람 1,200건 → 사건 37건」 | ★ 통념. 데모 문구는 필자 설계 |
| 관리도 오경보율 | 3σ 한계 단독이면 정상일 때 평균 약 371점마다 1번 오경보, WECO 규칙을 더하면 약 92점마다 1번 | NIST e-Handbook 관리도 절(근거 참조, E2). 알람 피로 자체는 ★(직관) |
| 관리한계 ≠ 규격한계 | → [품질·수율 관점](../품질-계측-후공정/01-품질-수율.md) 부록 지표 표(관리한계 ≠ 규격한계, Cp / Cpk). 다른 선·다른 색으로 | 필자 요약(외부 출처 미확인) |
| 가용도 4종 | 같은 이름 다른 정의 — 분자에 엔지니어링 시간을 넣나 × 분모에 비계획 시간을 넣나. 정비·생산·재무가 각자 다른 것을 센다 | INFICON 가용도 글(E3). 표는 [설비 관점](../흐름-설비-계획/02-설비.md) |

### 결정 직무와 데이터
- **결정 직무**: 공정·장비 엔지니어 전반.
  - 장비 엔지니어 직무 서술(셋업·점검·개조·개선, 이상 시 신속 대응, PM·부품 수급 — 뉴스룸 JOB로그 「양산기술」, 2025-04-30) → [설비 관점](../흐름-설비-계획/02-설비.md) 부록
  - 공정 엔지니어 직무 서술(레시피 조건 평가·측정 데이터 분석) → [계측·제어 관점](../품질-계측-후공정/02-계측-제어.md) 부록
  - 품질보증 직무 서술(영향·출하 가능 여부 확인, Excel·Python·JMP, 정상·불량 집단 비교 — 뉴스룸 「품질보증」, 2026-10-14) → [품질·수율 관점](../품질-계측-후공정/01-품질-수율.md) 부록 「결정 직무」
- **데이터**: 조치 기록(Inform Note), 알람 로그, 변경 이력, 인계 메모. 컬럼 예(전부 필자 설계 — 실제 과제의 열 이름은 반드시 `unique()` 로 확인):
  - 조치 기록 `note_id, eqp_id, chamber, occurred_at, symptom_text, cause_text, action_text, downtime_min, author_level` · 상태 이력 `eqp_id, state(RUN/IDLE/PM/DOWN/ENG), start, end` · 부품 `part_no, replaced_at, life_hours`
  - 알람(FDC) `timestamp, eqp_id, chamber, sensor_id, param, value, unit, ucl, lcl, usl, lsl, alarm_flag, severity` · 규정 문서(조항 번호·본문·개정일) · 로그 `ts, level, module, error_code, message`

### 흔한 고통
- **흔한 고통**
  - 서정원 TL·박우종 TL(뉴스룸 「품질보증」, E4)의 현직자 인용 둘 → [품질·수율 관점](../품질-계측-후공정/01-품질-수율.md) 부록 「흔한 고통 — 현직자 말」
  - Inform Note 에이전트 원문이 밝힌 기존 고통: 데이터 분석·가공에 오랜 시간, 표준화된 조치가 없어 동일 불량에도 대응이 제각각(GaiA 글, E2 자사). 숙련자 지식 의존(명장·마스터로 보완). 로그를 일일이 확인하고 표준을 찾는 데 오랜 시간 — 로그 분석 에이전트 글의 문제 서술(E2 자사).
  - FDC 의 높은 설정 비용·오경보·미탐 인용(Moyne & Iskandar, E2)과 센서 수백 개·알람 연쇄 → [설비 관점](../흐름-설비-계획/02-설비.md) 부록 「흔한 고통」.

### 현장 사람이 할 반문 — 상세
- **현장 사람이 할 반문**: ① 양산관리 「그 숫자, 우리 정의로는 다르게 나오는데요?」 ② 품질 「영향 범위는요?」 — 두 문구는 필자가 든 예시(추론)이고, ①은 「부서마다 해석이 다를 수 있다」(한진성 TL)에, ②는 「다른 제품으로 문제가 확대될 가능성까지 확인한다」(뉴스룸 「품질보증」)에 기댄다.
  - ③ 「AI 가 찾은 후보가 실제 어떤 위험이냐는 우리가 판단한다」 — 근거: 채용 담당 TL 발언(원문은 [품질·수율 관점](../품질-계측-후공정/01-품질-수율.md) 부록, 같은 기사, E4). ④ 「Inform Note 말고 다른 데이터도 붙나요?」(추론) — 원문 단서 「현재는 Inform Note 중심」, 다른 데이터 연동은 향후 계획.

### 6시간 최소 문제 — 상세
- **6시간 최소 문제**(추론): ① 조치 기록 텍스트 → 증상 유사 검색 → 원인·조치 후보(근거 note 인용). ② 알람 로그 → 같은 장비·시간창 묶기 → 사건 큐 + 「교대 인계 요약」 자동 초안(미해결 사건·진행 중 Q-time 로트·예정 PM). ③ 지표 사전(같은 이름 다른 정의) — 가용도 4종처럼 부서별 정의를 한 화면에 나란히 놓는 「데이터 의미 통일판」. 양산관리 TL 이 말한 주간 회의의 준비물을 자동으로 만드는 꼴.
  - 해법 틀·데모(필자 설계): ①은 증상 임베딩 검색 → 유사 사례 Top-k → LLM 이 원인·조치 요약(근거 note_id 인용 필수). 화면은 증상 입력창 → 추천 조치 카드 3장(근거 기록 펼치기·신뢰도·「이 조치로 해결됨」 피드백). ②는 관리한계·규격한계 분리 판정 → 알람을 사건으로 묶기 → 심각도·영향 로트 수로 우선순위, LLM 은 사건 요약 문장만.
    - 화면은 관리도(두 종류 한계 다른 색) · 사건 큐 · 전후 카운터. 합성 Inform Note 를 직접 만들면 꾸며 보이게 하지 말고 화면에 「합성」이라고 표시한다.
